# 录音内容对外分享：五种方案与选型

> 状态：调研稿，未实现
> 日期：2026-11-09
> 关联：[docs/14-feishu-live-brief.md](14-feishu-live-brief.md)、[docs/15-live-audio-listen.md](15-live-audio-listen.md)、[app/export.py](../app/export.py)、[app/server.py](../app/server.py)、[app/feishu.py](../app/feishu.py)、[tools/feishu_bot.py](../tools/feishu_bot.py)

## 0. 结论先行

1. **先定分享单位，再选通道。** 绝大多数场景要分享的不是「13 小时整场录音」，而是「某个观点 + 那 30 秒原声 + 一句原话」。把分享单位定成 **片段（clip）+ 摘要 + 时间码**，体积、隐私、体验三个问题同时小一个量级。
2. **没有单一方案覆盖全部受众。** 组织内、外部客户、自己多设备，三类的可达性和权限模型完全不同。推荐组合：
   - 组织内：**飞书消息/云文档/云盘（方案 A）**，卡片只做入口。
   - 外部：**对象存储 + 只读分享页（方案 D）**，这是唯一能同时保住「时间轴联动 + 权限可控 + 可审计」的路线。
   - 快速验证：**飞书妙记（方案 B）**，但它是另一套转写，不继承我们的校对、术语、说话人。
   - 兜底/归档：**离线分享包（0 号基线）**。
   - 第三方云盘（方案 C）只做非敏感、一次性的外发；内网穿透（方案 E）只做内部演示，不进正式方案。
3. **今天最该先补的不是「上传到哪」，而是三件基础设施**：音频转码（WAV 太大）、分享鉴权（现在服务完全没有鉴权）、可达性（现在只有局域网）。任何方案都绕不开这三件。
4. **不建议把整场 WAV 直接发飞书或网盘。** 一场 13 小时 40 分的录音是 1.49 GB，上传、下载、预览都痛苦；转 opus 24 kbps 后约 140 MB，仍然只适合「整场归档」，不适合「发给别人听」。

## 1. 现状约束（代码与运行事实）

| 项 | 现状 | 对外分享的含义 |
|---|---|---|
| 音频 | `data/audio/LIVE_*.wav`，16 kHz / 单声道 / s16le，**32 KB/s = 115 MB/小时**；最长一场 `LIVE_20261108_224302.wav` 约 1.49 GB；当前 `data/audio` 共 3.3 GB | 直接外发不现实，必须先转码 |
| 回听 | `/api/audio` 支持 Range；`/reader?session=&t=` 时间轴联动；采集中读 spool | 体验已经很好，但只在本机/局域网 |
| 导出 | `/api/export?fmt=md\|srt`，只有文字，没有音频打包 | 「离线分享包」需要补一步转码与打包 |
| 鉴权 | 服务默认绑 `127.0.0.1`，无登录、无 token、无只读路由 | 暴露到公网前必须先做分享令牌，不能直接穿透 |
| 地址 | `BASE_URL` 自动取本机局域网 IP（示例 `http://192.168.1.10:8765`；多网卡选错时用 `LIVENOTES_BASE_URL` 覆盖） | **卡片里的「回听」链接转发出去一定打不开** |
| 飞书 | 长连接（无公网回调），已实现文本/卡片；**未实现文件上传**；owner 私聊 + 群白名单 | 发音频片段要补 `im/v1/files` + opus 转码；文件上传到云盘要补 drive 权限 |
| 存储 | SQLite 单机，无对象存储、无域名、无备案、无账号体系 | 方案 D 需要新增外部依赖 |
| 数据形态 | 逐字稿有说话人、术语纠错、校对结果；总结/高光是 LLM 产物 | 这些是我们的差异化资产，妙记/网盘都带不走 |

**一句话**：现有架构「内部体验完整、外部完全不可达」。分享方案的本质，是选一种方式把「时间轴 + 文字 + 原声」这三样东西送出去，同时决定谁能在什么期限内看。

## 2. 分享的到底是什么：三层内容，三种敏感度

| 层 | 内容 | 体积 | 敏感度 | 建议默认 |
|---|---|---|---|---|
| L1 摘要 | 阶段性总结、要点、高光理由 | KB | 低 | 可较广分享；外部需确认无客户名/金额 |
| L2 逐字稿 | 带说话人、时间码的全文 | 几十 KB ~ 几百 KB | 中 | 指定人；可脱敏说话人（主播/嘉宾） |
| L3 原声 | WAV/片段，含主播声音、背景、连麦 | 1.5 GB / 140 MB | 高 | 限时、限人、可撤销；默认只给片段 |

三条产品原则：

1. **默认分享 L1 + 片段 L3**，不默认给整场原声。
2. **时间码必须能点。** 截图中「回听」链接的价值就是「这句话在第 49 秒」；丢了时间轴，分享退化成一段文字。
3. **分享是有期限的。** 录音涉及第三方主播与说话人身份，链接应带过期时间与撤销能力。

合规提醒（不是法律意见）：抖音直播录音的再分发涉及平台 ToS 与主播授权；说话人声纹/身份属于个人信息。对外分享前至少要确认「有没有授权」「对方是谁」「多久删除」。

## 3. 五种方案

### 方案 A：飞书消息 + 云文档 + 云盘（「飞书自带」之一）

**形态**

- 摘要/要点 → 飞书文档（docx）；每条要点带时间码与「回听」链接。
- 音频 → 转 opus/m4a 后作为群文件、云盘文件或语音消息发出；逐字稿 `.md` / `.srt` 一并附上。
- 权限用飞书原生：组织内可见、指定人、链接分享、禁止下载/水印（视租户版本）。

**复用现有资产**：`/api/export` 的 Markdown/SRT 直接可用；飞书卡片已经是入口；`app/feishu.py` 已有发文本/卡片能力。

**优点**

- 零新增基础设施，权限体系成熟，手机端体验好，评论/@/留痕都现成。
- 组织内同事不需要新账号，转发路径最短。
- 内容留在飞书租户内，合规上比个人网盘好解释。

**缺点**

- **音频与时间轴割裂**：飞书文档里点时间码不能跳到音频第 N 秒；音频是附件/独立消息。
- 大文件上传慢、有单文件上限；1.5 GB 整场基本不可行。
- 外部（非本组织/不同租户）分享受管理员策略限制，常常默认关闭。
- 校对结果更新后要重新导出、重新上传，版本容易乱。
- 机器人目前没有文件上传能力，要补 drive / im 文件接口与权限申请。

**适用**：组织内同事、周报式交付、以文字为主的复盘。

**工作量**：1~2 天（导出 docx + 转码上传脚本），不含租户权限沟通。

---

### 方案 B：飞书妙记（Minutes）

**形态**：把音频/视频上传到妙记，妙记自动转写，生成「播放器 + 转写文本 + 时间轴」的分享链接；支持评论、搜索、导出文字。

**优点**

- 最接近「带时间轴的录音分享」的现成产品，手机/网页都能听，链接可转发。
- 不依赖我们的服务在线；对方不需要装任何东西。
- 转写与音频天然对齐，搜索、倍速、跳转都是现成的。

**缺点**

- **二次转写**：我们的术语表、逐字校对、说话人聚类、总结/画像都带不过去；专有名词错误会重新出现。
- 长音频上传与转写有时长/体积/租户版本限制，**具体上限必须先验证**。
- 开放接口目前主要覆盖读取/统计，程序化「上传即建妙记」的能力受租户与版本限制，需要核实。
- 内容进入飞书云，涉及第三方主播原声时的合规判断与方案 A 相同。
- 无法嵌入我们的高光榜、关注词、主播画像。

**适用**：对方要飞书原生体验、需要评论协作、能接受「重新转一遍」的整场回听。

**工作量**：0.5~1 天验证租户能力 + 人工流程；自动化取决于 API 是否开放。

---

### 方案 C：第三方云盘（阿里云盘 / 百度网盘 / OneDrive / Google Drive）

**形态**：导出 `summary.md` + `transcript.srt` + `audio.opus/m4a`（+ 可选静态 HTML 报告）→ 打包 zip → 上传 → 生成带提取码/有效期的分享链接。

**优点**

- 零开发，现有导出直接复用；大文件友好；跨组织、跨平台；成本低。
- 对方没有飞书也能收，适合一次性交付。

**缺点**

- **完全没有时间轴联动**，在线播放限速/要客户端，体验最差。
- 公司内容放个人网盘有合规风险；链接二次扩散不可控；无访问审计。
- 国内网盘外链有审核/限速；海外盘（Google Drive/OneDrive）国内访问不稳定。
- 版本更新要重新上传、重新发链接。

**适用**：非敏感、一次性、对方没有飞书且不需要回听定位。

**工作量**：0.5 天打包脚本。

---

### 方案 D：对象存储 + 只读分享页（推荐中长期）

**形态**

- 新增 `shares` 表：`token`、`session_id`、时间范围（整场/片段）、内容开关（原声/逐字稿/总结）、过期时间、可选密码、访问计数。
- 音频转 **opus 24~32 kbps 或 AAC 48 kbps**，存对象存储（OSS/COS/R2）；播放地址用**短期签名 URL**，页面本身用 `/s/<token>`。
- 分享页复用现有 reader：时间轴联动、说话人、总结、原话；去掉校对/编辑/管理接口，只读。
- 飞书卡片里的「回听」在外部分享场景改成分享页 URL；内部仍可用局域网 reader。

**复用现有资产**：reader 前端、时间轴、说话人、总结、导出；`docs/15` 已设计的切片/转码思路可直接用。

**优点**

- 体验最好：点时间码听原声，和截图里的卡片体验一致，但对外可达。
- 权限可控：随机 token、过期、撤销、密码、下载开关、访问统计。
- 音频体积降一个数量级（1.5 GB → 约 140 MB），流量成本可算。
- 可做品牌化交付页，后续能加封面、章节、高光导航。

**缺点**

- 1~2 周开发（分享模型 + 转码 + 签名 + 只读页 + 测试）。
- 新增公网资产：域名、HTTPS、备案（国内对象存储自定义域名）、签名/防盗链/限流、备份。
- 安全责任更明确：一旦泄露，是我们自己的链接问题，不是飞书/网盘的问题。
- 第三方主播原声的版权/合规风险在「公开链接」形态下更高，必须默认短有效期 + 禁止索引。

**适用**：对外分享常态化（每周 ≥1 次）、对象含客户/合作方、需要「给链接就能听」。

**工作量**：MVP 7~10 人天；不含备案等待。

---

### 方案 E：内网穿透临时分享（Cloudflare Tunnel / frp / Tailscale）

**形态**：给现有服务加一条只读 token 路由（如 `/s/<token>`），用 tunnel 暴露到公网；或 Tailscale 只邀请指定人进内网。

**优点**

- 1~2 天可上线，完全复用现有页面和音频，不转码、不搬家。
- 适合内部演示、小范围试用、临时救急。

**缺点**

- **依赖这台机器一直在线**：内存吃紧、重启、断网都会让链接失效；没有 SLA。
- 家庭/办公宽带上行有限，多人同时听会卡。
- 现有服务无鉴权，穿透前必须新增只读路由、token、限流；否则等于把整个管理接口暴露。
- 安全面扩大（公网扫描、暴力尝试），不适合正式对外。

**适用**：内部小范围验证需求，不作为长期方案。

**工作量**：1~2 天（含只读路由与 token）。

---

### 0 号基线：离线分享包（兜底与归档）

- 内容：`summary.md` + `transcript.srt` + `audio.opus/m4a` + 可选封面/高光清单，打成一个 zip。
- 优点：零依赖、可归档、外部任何人可收、离线可看。
- 缺点：不能点时间码回听、不可更新、大文件传输麻烦。
- 定位：所有方案的兜底形态；也是「录音保留期到期前」的归档产物。

## 4. 对比矩阵

| 维度 | A 飞书文档/云盘 | B 妙记 | C 第三方云盘 | D 对象存储+分享页 | E 内网穿透 |
|---|---|---|---|---|---|
| 组织内可达 | ★★★★★ | ★★★★★ | ★★★ | ★★★★ | ★★★★ |
| 外部可达 | ★★（受租户策略） | ★★★★ | ★★★★★ | ★★★★★ | ★★★（需装/登录） |
| 时间轴联动 | ★（文字与音频割裂） | ★★★★★ | ★ | ★★★★★ | ★★★★★ |
| 保留我们的校对/术语/说话人 | ★★★★★ | ★ | ★★★★（导出文件） | ★★★★★ | ★★★★★ |
| 权限/过期/撤销/审计 | ★★★★（飞书原生） | ★★★ | ★ | ★★★★★ | ★★ |
| 音频体积/流量 | ★★（大文件） | ★★★ | ★★★ | ★★★★★（opus） | ★★（WAV） |
| 工作量 | 1~2 天 | 0.5~1 天验证 | 0.5 天 | 7~10 天 | 1~2 天 |
| 依赖本机在线 | 否 | 否 | 否 | 否 | **是** |
| 合规风险 | 中（租户内） | 中（飞书云） | 高（个人盘） | 中（需自控） | 高（无鉴权面） |
| 长期可运维 | ★★★★ | ★★★ | ★★ | ★★★★★ | ★ |

**读法**：如果只看「组织内 + 快」，选 A；如果只看「外部 + 体验」，选 D；B 是唯一「今天就能有带时间轴分享链接」的现成产品，但会丢掉我们的核心资产；C/E 是补位，不是主线。

## 5. 成本与体积测算（量级，不是报价）

| 格式 | 码率 | 每小时 | 13 小时一场 | 相对 WAV |
|---|---|---|---|---|
| WAV 16k mono | 256 kbps | 115 MB | ~1.5 GB | 1× |
| Opus | 24 kbps | 10.8 MB | ~140 MB | ~1/10.7 |
| Opus | 32 kbps | 14.4 MB | ~187 MB | ~1/8 |
| AAC-LC | 48 kbps | 21.6 MB | ~280 MB | ~1/5.3 |

- 单场 150 MB、100 次完整播放 ≈ 15 GB 流量；按国内对象存储外网流量 0.5 元/GB 量级，约 7~10 元/场。**存储不是瓶颈，带宽和权限才是。**
- 飞书云盘/妙记的容量与单文件上限取决于租户套餐，需实际验证。
- 转码成本可忽略：ffmpeg 单路 13 小时音频转 opus 是分钟级，可在收尾阶段异步做。

## 6. 安全与合规清单（任何方案都要回答）

1. **授权**：录音来自第三方直播，再分发是否有主播/平台授权？默认只做内部，外发逐次确认。
2. **脱敏**：说话人默认显示「主播 / 嘉宾」，真名与声纹不随分享页出去。
3. **令牌**：≥128 bit 随机、不可枚举、可撤销、带过期；分享页与音频 URL 都要签名。
4. **下载**：默认关闭原声下载；页面可下载时加水印或至少记录访问者。
5. **索引**：`robots noindex`，不生成公开目录，不被搜索引擎收录。
6. **审计**：谁、何时、看了哪一段、是否下载；至少进现有事件流。
7. **保留期**：录音 30/90 天自动清理；分享链接与录音同生命周期，录音删除则链接失效。
8. **限流**：分享页与音频端点独立限流，防爬、防批量拖库。
9. **合规提示**：分享页顶部写明用途与禁止转发；外发前由人确认，不自动群发。

## 7. 推荐路线（分阶段）

### 第 0 步：本周，0.5~1 天，零新基础设施

- 定「分享包」标准：`summary.md` + `transcript.srt` + `audio.opus`（按需片段）+ 封面。
- 飞书内部分享用「文档 + 片段」：摘要进文档，原声只发片段（复用 `docs/15` 方案 B 的转码/上传思路）。
- 明确一条规则：**整场 WAV 不外发**；对外只给片段或分享页。

### 第 1 步：2~3 天，验证妙记

- 用一场 30~60 分钟的真实录音验证：能否上传、转写质量、时长/体积上限、分享到外部租户的策略、导出格式。
- 若可用：作为「对方要飞书原生体验」的快速通道；不作为主链路。
- 若不可用：直接进入第 2 步，不纠缠。

### 第 2 步：1~2 周，按触发条件决定是否做 D

满足任意两条就立项：

- 外部分享每周 ≥1 次；
- 对方没有飞书或跨租户；
- 需要「点时间码听原声」；
- 需要链接过期/撤销/访问统计；
- 内容含客户信息，不能放个人网盘。

D 的 MVP 范围建议：单个分享页 + 片段级分享 + opus 转码 + 签名 URL + 过期/撤销 + 访问计数；先不做多租户、评论、水印。

### 不做 / 缓做

- **E 内网穿透**：只在内部演示时临时用，穿透前必须加只读 token 路由；不进正式方案。
- **C 第三方云盘**：只做非敏感兜底，不作为对外主通道。
- **整场音频进飞书群**：1.5 GB，体验和合规都不划算。

## 8. 待拍板

1. **分享对象主要是谁？** 组织内同事 / 外部客户 / 公开链接。这决定 A 还是 D。
2. **是否必须「点时间码听原声」？** 如果只要文字 + 整段音频，A/C 就够了，D 可以不立项。
3. **单场时长与分享频率？** 13 小时是极端值；如果多数是 1~2 小时，体积压力小很多。
4. **是否接受内容进飞书云/第三方云？** 涉及合规与客户数据。
5. **是否已有域名、备案、云账号？** 决定 D 是 7 天还是 3 周（备案可能占大头）。

## 9. 收敛：只考虑飞书内部（2026-11-09 追加）

> 前提：排除第三方云盘（方案 C）与对象存储（方案 D）；飞书自带的云盘/群文件仍算内部能力。如果连飞书云盘也不用，就只剩「消息 + 云文档 + 妙记」三件。

### 9.1 先把体积压下来

`data/audio` 实测：

| 场次 | WAV | 时长 | opus 24 kbps |
|---|---:|---:|---:|
| LIVE_20261108_224302 | 1422 MB | 12.94 h | ~140 MB |
| LIVE_20261108_224740 | 853 MB | 7.76 h | ~84 MB |
| LIVE_20261107_233921 | 128 MB | 1.16 h | ~13 MB |
| 1 小时典型场 | 115 MB | 1 h | ~11 MB |

- 1.4 GB 不是异常，是**未压缩 PCM**：16 kHz × 16 bit × 单声道 = 32 KB/s = 115 MB/h；12.94 h 就是 1.49 GB。普通 1~2 小时场只有 115~230 MB。
- 转 opus 24 kbps 后约为原来的 **1/10.7**；当前 `data/audio` 3.3 GB → 约 **310 MB**。
- 纯语音场景 24 kbps 足够听清内容；要保留音乐/现场氛围可用 32 kbps（13 h 约 187 MB）。
- **不建议**采集端降到 8 kHz（ASR 识别率会掉），也**不建议**只存 VAD 人声段（时间轴和「当时确实安静」的证据会丢）。

落地方式（不改采集链路）：收尾时异步 `ffmpeg → opus`，更新 `audio_path`；WAV 按保留期删除（如 7 天，或只对标记「要复听」的场次保留）。reader 播放切到 opus，Safari 用 m4a 兜底。代价是一次分钟级转码和少量实现工作，收益是磁盘、上传、备份都小一个数量级。

### 9.2 飞书内部只有四种容器

| 容器 | 放什么 | 给谁 | 关键限制 |
|---|---|---|---|
| 消息（语音/文件） | 30 秒~5 分钟 opus 片段、整场 opus 文件 | 私聊/群 | 语音有时长上限；群发不可撤回；文件有单文件上限 |
| 云文档 | 摘要、要点、原话、时间码、附件 | 组织内/互联网链接（看策略） | 不能内嵌我们的播放器；点时间码不能跳音频 |
| 妙记 | 整场音频 + 自动转写 + 播放器 | 组织内/外部分享（看策略） | 二次转写，术语/说话人/校对不继承；上传限制需验证 |
| 云盘/群文件 | 整场 opus、分享包 zip | 组织内/外链 | 只是存放，没有时间轴体验 |

### 9.3 推荐组合：转码 + 片段 + 妙记

1. **片段是主产品（覆盖 80% 场景）**：`/分享 CH01 90秒` 或卡片上「分享这段」→ 切 opus → 机器人发语音消息 + 一句话摘要 + 原话 + 起止时间。对方听到的就是那 90 秒，不需要时间轴。复用 [docs/15](15-live-audio-listen.md) 方案 B 的转码/上传/限流设计。
2. **妙记是整场兜底**：收尾后把 opus 上传妙记，卡片里「整场回听」指向妙记链接。适合「我要从头听一遍」的少数场景。
3. **云文档做沉淀**：周报/复盘把多场摘要、原话、妙记链接汇总成一篇；不做回听入口。
4. **群文件/云盘做归档**：整场 opus（140 MB/13 h），不再保留 WAV。

分享单位仍然是「摘要 + 原话 + 片段」，不是整场。飞书内没有「点第 49 秒」的精确跳转，替代品是「这个片段就是第 49~79 秒」。

### 9.4 飞书-only 能得到什么、失去什么

**得到**：零新基础设施；权限、评论、移动端现成；组织内转发顺；外部可通过互联网链接分享（取决于租户策略）。

**失去**：reader 的时间轴联动；访问审计与细粒度撤销（依赖飞书权限）；我们校对后的逐字稿与音频同步展示；分享页的品牌化。

**最大不确定性**（见附录，必须先验证）：

- 妙记是否支持本租户上传本地音视频，单文件体积/时长上限是多少；
- 妙记是否支持导入 SRT/字幕——若支持，二次转写的短板基本补上；
- 妙记分享链接是否支持 `t=` 秒数参数——若支持，卡片就能直接跳到秒。

### 9.5 落地顺序与工作量

| 步骤 | 内容 | 工作量 | 状态 |
|---|---|---|---|
| P0 | 收尾转码 + 保留策略 + reader 播放切换 | 1~2 天 | 已落地 |
| P1 | 机器人发片段（`/分享`、卡片按钮、限流、降级） | 2~3 天 | 已落地 |
| P2 | 妙记分享包 + 链接回填（人工上传） | 0.5~1 天验证 | 已落地 |
| P3 | 云文档模板（周报/复盘） | 1 天 | 已落地 |

总计约 1 周，不含租户权限申请。**不建议**在飞书里复刻 reader 的时间轴；那是方案 D 的活。飞书-only 接受「片段即证据」。

### 9.6 实现说明（2026-11-09，分支 `feat/recording-share`）

**P0 转码与保留**（`app/audio.py` + `app/config.py` + `app/store.py`）

- 收尾 `finish_session` 后异步转码：WAV/PCM → **AAC-LC m4a 32 kbps**（`<sid>.m4a`），更新
  `audio_path`/`audio_format`/`audio_bytes`/`audio_transcoded_at`，原 WAV 记在
  `audio_original_path`。选 m4a 而不是 opus 是为了 Safari / 飞书 WebView 直接能播。
  实测 13.3 MB（约 7 分钟）WAV → 1.7 MB m4a，转码 2.4 秒（约 170× 实时）；按此推算
  1 小时约 14 MB、13 小时约 180 MB，`data/audio` 3.3 GB 全量补转约 10 分钟。
- 服务启动时 `start_backfill()` 扫描历史 WAV 补转码，`start_sweeper()` 每小时跑一次
  保留清理：原 WAV 默认留 7 天，m4a 默认永久（设 0 以外的天数才清）。
- `/api/audio` 的 `Content-Type` 按扩展名给；`t_start/t_end` 切片对 m4a 走
  `ffmpeg -ss/-to`，reader 时间轴不需要改前端。
- 阅读页/回听链接仍是局域网地址，转码只解决体积，不解决外发。

**P1 片段分享**（`app/clips.py` + `app/feishu.py` + `tools/feishu_bot.py`）

| 命令 | 行为 |
|---|---|
| `/分享 CH01 90秒` | 最近 90 秒（5~300 秒，默认 90） |
| `/分享 CH01 1:30` | 从 1:30 起 90 秒 |
| `/分享 CH01 1:30 2分钟` | 从 1:30 起 2 分钟 |
| `/确认分享 <码>` | 群聊二次确认（5 分钟有效） |

- 片段按需切 Ogg Opus 24 kbps 缓存 2 分钟，优先发飞书**语音消息**；上传失败降级发
  文件。发送成功后再带一句「🎧 CH01 90秒 · 摘要/原话/起止时间」，避免出现
  「有抬头、没音频」的半条消息。
- `最近 N 秒` 从已录末尾往前推（不是从 0:00 开始）；上传失败重试 3 次、客户端超时
  60 秒；语音和文件都失败时发一张带「重试」按钮的卡，且不占 30 秒冷却。
- 主人私聊直发；白名单群聊必须先出确认卡（音频不可撤回）。同一路 30 秒内限一次。
- 话题/总结/控制台卡片都加了「分享最近90秒」按钮。

**P2 妙记分享包**（`app/share.py` + `tools/share_package.py`）

- `build_package()` 生成 `summary.md` + `transcript.srt` + `audio.m4a` + `README.md` +
  `meta.json`，可压 zip；`zip_package()` 用 ZIP_STORED（音频已压缩）。`data/share` 默认
  7 天清理。
- 机器人 `/分享包 [CH]`（仅私聊）发 zip；`/妙记 CH01 <链接>` 回填 `sessions.minutes_url`；
  `/回听 CH01` 优先给妙记链接，没有则给局域网地址并提示外发要先上传。
- 简报/总结卡片在回填后追加「整场回听 <妙记链接>」。
- 妙记仍**没有**程序化上传：先人工上传 `audio.m4a`，再回填链接；等租户验证通过再谈自动化。

**P3 周报/复盘**（`app/report.py` + `tools/weekly_report.py` + `tools/feishu_bot.py`）

| 命令 | 行为 |
|---|---|
| `/周报` | 最近 7 天：多场摘要 + 原话 + 妙记链接汇总成一篇 |
| `/周报 上周` | 上周一 ~ 上周日；也支持 `本周`、`今天`、`7天`、`11-03~11-09` |
| `/复盘 [范围]` | 同样的数据面 + 逐场回顾 + 跨场观察，并留出「结论/行动」待填区 |

- **素材优先级**：已生成的整场总结 > 高光片段 > 高权重原句。没有总结的场次会标明
  「自动提取」，不会整段空白；筛选口径的总结不会被当成整场结论。
- **不写局域网回听入口**：文档里只放摘要、原话、时间码和妙记链接，符合 9.3 的
  「云文档做沉淀，不做回听入口」；这也避免了转发后点开是个打不开的地址。
- **短场 / 超量场次只列标题**：`< 3 分钟且没生成过总结`的场次不展开；重点场次超过
  30 场时按「有总结优先、时长次之」保留，避免报告变成逐字稿目录。
- **云文档**：机器人优先调 `docx/v1` 的 Markdown 转换 + 建文档，把正文一次写入；
  建好后通过 `drive/v1/permission_member` 把文档授权给发起人（`full_access`）。
  应用用 tenant token 建的文档归应用所有，默认不在任何人的「我的空间」里，
  不授权时用户点开只会看到无权限；授权失败不影响文档本身，消息里会标「自动授权失败」。
  租户没开 `docx:document`、`docx:document.block:convert` 或 `drive:drive` 时，自动
  降级为发送 `.md` 文件，并在消息里给出失败原因。`FEISHU_DOC_FOLDER_TOKEN` 可指定
  存放文件夹，`FEISHU_DOC_URL_BASE` 用于拼租户域名（如 `https://xxx.feishu.cn/docx/`）。
- 报告落在 `data/reports/`，默认保留 30 天，和分享包一起由音频清理线程定期清。

**新增环境变量**

| 变量 | 默认 | 说明 |
|---|---|---|
| `LIVENOTES_AUDIO_AAC_BITRATE` | `32k` | 归档 m4a 码率 |
| `LIVENOTES_AUDIO_OPUS_BITRATE` | `24k` | 飞书片段 opus 码率 |
| `LIVENOTES_WAV_RETENTION_DAYS` | `7` | 原 WAV 保留天数，`0` = 不删 |
| `LIVENOTES_AUDIO_RETENTION_DAYS` | `0` | 归档 m4a 保留天数，`0` = 永久 |
| `LIVENOTES_FFMPEG` | 空 | 指定 ffmpeg 路径；不填走 PATH |
| `FEISHU_DOC_FOLDER_TOKEN` | 空 | 周报云文档存放文件夹；空 = 机器人自己的空间 |
| `FEISHU_DOC_URL_BASE` | `https://feishu.cn/docx/` | 拼租户文档链接的域名前缀 |

**命令行**

```bash
python tools/share_package.py --session LIVE_20261109_140948
python tools/share_package.py --session LIVE_... --no-audio --out D:/tmp/share
python tools/share_package.py --session LIVE_... --minutes https://xxx.feishu.cn/minutes/xxx
python tools/weekly_report.py --range 上周
python tools/weekly_report.py --kind retro --range 7天 --doc
```

**尚未验证 / 已知边界**

- 真实租户下妙记的上传体积上限、外部分享策略仍要按附录清单验证。
- 飞书语音消息的 opus 时长/体积上限未在真实租户压测；超限会走文件降级。
- 转码后 reader 的 `t=` 跳转依赖 ffmpeg 输入 seek，长文件首次切片会比 WAV 慢。
- 云文档接口需要租户给应用开 `docx:document`、`docx:document.block:convert` 与
  `drive:drive`；没开时 `/周报` 会降级发 `.md`，不会失败。`docx` 的 Markdown
  转换单篇上限未在真实租户压测，超限同样走文件降级。
- 应用建的文档在应用云空间，不自动出现在「我的空间」；已自动授予发起人
  `full_access`。要把文档放进团队共享文件夹，配置 `FEISHU_DOC_FOLDER_TOKEN`，
  并确认应用对该文件夹有编辑权限。真实租户已验证建文档（267 块）、写入正文与
  授权给发起人（2026-11-10）；妙记的租户策略与外部转发限制仍需按场景确认。
- 周报的「高频话题」来自已生成总结/逐句话题标签；没有跑过 AI 标注的场次只能拿
  到较粗的类别标签，话题统计会偏少。

## 附：需要向飞书/云厂商核实的能力清单

> 以下为调研中无法从本仓库确认、需用真实租户验证的项，避免方案建立在错误假设上。

- 妙记：本租户是否允许上传本地音视频；单文件时长/体积上限；能否分享给外部租户；是否有「上传即建妙记」的开放接口。
- 飞书文档（docx）：开放接口能否插入音频/文件块；文档内链接能否带时间参数跳转。
- 飞书云盘：单文件上限、上传限速、机器人是否需要额外 drive 权限与文件夹 token。
- 飞书消息：`im/v1/files` 的 opus 时长/体积上限；语音消息在移动端的转发限制。
- 对象存储：国内 OSS/COS 自定义域名备案要求与费用；Cloudflare R2 国内访问质量；签名 URL 与 CDN 的组合方式。
- 浏览器兼容：iOS Safari 对 Opus 的支持情况，决定是否需要 AAC/m4a 兜底。
