# 实时监听：只录一个直播标签页

## 它做什么

页面右上角「● 实时监听」→ 选择正在播放的抖音直播标签页 → 勾选「分享标签页音频」。

浏览器只把**被选中标签页**的音频推给本地服务，所以微信提示音、其他网页的声音都不会混进来，也不需要装虚拟声卡。

链路：

```
标签页音频 --getDisplayMedia--> AudioWorklet(16k/int16) --POST 256ms一块-->
  silero VAD 断句 -> SenseVoiceSmall 转写 -> CAM++ 声纹在线聚类 -> SQLite
  -> 页面实时字幕 / 逐字稿 / 现有总结
```

## 三种采集底座

同一个代理（`tools/capture_agent.py`）有三套采集底座，用 `LIVENOTES_CAPTURE_MODE` 选：

| 模式 | 怎么采 | 适合 |
|---|---|---|
| `per_room`（默认） | 每个房间拉起一个专属 Chrome，打开 `/capture` 采集页，走 `getDisplayMedia` | 1~3 路；互相隔离，一个浏览器崩了不影响其它路 |
| `shared`（实验性） | 一个 Edge 开 N 个直播间标签页，扩展往每个标签页注入采集脚本，走 `video.captureStream()` | 3~5 路，想省内存 |
| `direct`（抖音） | 从 reflow 页取播放地址，ffmpeg 直接拉音频，不加载页面 | 抖音 1~5 路；最省内存；失败停下等你确认切换 |

浏览器选择：`per_room` 用 Chrome 正式版优先，找不到才用 Edge；`shared` 反过来优先 Edge，
因为 Chrome 正式版 137 起忽略 `--load-extension`，要 Chrome 只能用 Chrome for Testing
并通过 `LIVENOTES_SHARED_BROWSER` 指定。direct 失败后默认**不自动切**：收听页会亮出
「切换浏览器采集」，你点了确认才走 `per_room`（Chrome 优先）或 `shared`。这个策略在
「⚙ 设置 → 采集」里可改（`ask` / `auto` / `none`），采集代理每 3 秒同步一次，改完立即生效；
环境变量 `LIVENOTES_DIRECT_FALLBACK` 是脚本级覆盖，设了就优先于设置页。

### shared 模式的链路

```
标签页 <video> --captureStream()--> AudioContext(16k) --ScriptProcessor(4096)-->
  int16 PCM -> base64 -> chrome.runtime.sendMessage -> service worker -> POST /api/live/chunk
```

几个关键点：

- **为什么不用 `tabCapture`**：`chrome.tabCapture.getMediaStreamId` 对扩展自己创建的标签页
  要求 activeTab / 用户手势，后台开出来的标签页会报「Extension has not been invoked for
  the current page」；`captureStream()` 没有这个限制。
- **标签页静音不影响采集**：`chrome.tabs.update({muted:true})` 只掐扬声器输出，实测
  `captureStream` 的 RMS 不变，所以多路同时监听不会一起外放。
- **后台标签页会被抖音暂停**：抖音在标签页隐藏时暂停 `<video>`。隐藏标签页的
  `setInterval` 会被节流，但 `ScriptProcessorNode.onaudioprocess` 仍按 4 块/秒触发，
  所以把「暂停就 `play()` 拉回来」放在音频回调里，每 4 块检查一次。
- **控制面**：MV3 service worker 会休眠，代理用扩展的 `panel.html` 当稳定的 CDP 控制页，
  所有 `chrome.runtime.sendMessage` 都从这一页发，顺便把 service worker 唤醒。
- **浏览器要求**：Chrome 正式版从 137 起忽略 `--load-extension`，所以默认用 Edge，
  找不到再用 Chrome for Testing；也可用 `LIVENOTES_SHARED_BROWSER` 指定 exe。
- **扩展被禁用**：Edge 非正常退出后可能把未打包扩展标成 disabled（Secure Preferences 里的
  `disable_reasons`），代理启动时会检测并清掉这个标记，然后重新加载。

### direct 模式的链路（只支持抖音）

```
webcast.amemv.com/douyin/webcast/reflow/<id>（分享短链先跟一次跳转）
  -> 抓 HTML 里现成的 <webcast-reflow-player url="...flv...">（约 0.5 秒）
  -> FLV 地址（约 7 天有效）
  -> ffmpeg -vn -ac 1 -ar 16000 -f s16le pipe
  -> 重新切块成 4096 样本（8192 字节） -> POST /api/live/chunk
```

几个关键点：

- **会话由代理自己建**：浏览器模式是采集页调 `/api/live/start`；direct 模式下代理先建会话
  （`source_mode=direct`），再把音频按 `X-Live-Id` 推给同一个 `/api/live/chunk`，服务端
  不需要区分音频从哪来。
- **为什么从 reflow 页取流**：抖音新版 `live.douyin.com` 把房间数据挪进了客户端脚本，
  streamlink 的插件扒不到（实测返回 `No playable streams found`）；而分享落地页
  `webcast.amemv.com/.../reflow/<id>` 的 HTML 里直接嵌着播放地址，稳定且快。
  streamlink 只在 reflow 页拿不到地址时兜底，没装也不影响直取。
- **不要改写房间 URL**：reflow 后面的 `<id>` 有时是分享/回流 id，不是 `web_rid`；
  把它直接换成 `live.douyin.com/<id>` 会被抖音回「服务器开小差了」。房间保留原链接，
  浏览器回退也能打开。
- **失败不自动切换**：解析失败、ffmpeg 起不来、首块 8 秒没到、或运行中连续 15 秒没块，
  先按下面的运行中自愈重试；超过 3 次就把房间停在 `failed`，在房间卡片/详情里亮出
  「直取失败 · 切换到浏览器采集」。**只有你点了确认**（`POST /api/rooms/switch`）采集代理
  才会拉起浏览器。会话先留着（服务端看门狗 120 秒后收尾），马上确认就能接着同一场录。
  策略默认 `ask`，可在「⚙ 设置 → 采集」里改成 `auto`（自动切浏览器）或 `none`（只报错）；
  设环境变量 `LIVENOTES_DIRECT_FALLBACK` 则覆盖设置页。
- **运行中自愈**：ffmpeg 退出或 15 秒没新块，先重新解析、重启 ffmpeg，沿用原会话，最多 3 次；
  超过 3 次才停下来等你确认切换。
- **分块大小**：ffmpeg 输出的是连续字节流，代理按 4096 样本（256ms）重新切块，
  和服务端 `AudioWorklet` 的块大小一致，VAD/看门狗的行为不变。
- **下播判断**：沿用代理原有的页面探针（`LIVENOTES_RECHECK_SECONDS`）；探针发现下播就停会话。
  服务端 120 秒断流看门狗仍然兜底。
- **依赖**：只需要 `ffmpeg` 在 PATH；`streamlink` 是可选兜底
  （`pip install -r requirements-direct.txt`，不装也能直取）。
  启动用 `tools\start_direct.bat`（它把回退设为 `ask`），
  或先 `set LIVENOTES_CAPTURE_MODE=direct` 再运行 `tools\start.bat`；
  `tools\stop.bat` 不需要改，停掉代理后 ffmpeg 会因管道关闭自行退出。

### direct 模式的边界

- **只支持抖音**：B 站、快手暂不实现。非抖音链接会停在「直取失败」，确认后走浏览器模式。
- **流地址会过期**：抖音 FLV 地址约 7 天；代理每次重建都会重新解析，不缓存过期地址。
- **部分房间需要登录态**：付费/私密/地区限制的房间可能解析失败，此时停在待切换，确认后走浏览器。
- **「服务器开小差了」不等于下播**：它是抖音的通用错误提示，直播间可能开着；现在只作为
  临时故障提示，不会再把房间判成「没在播」。
- **不要边录边切模式**：切换 `LIVENOTES_CAPTURE_MODE` 前先停掉正在听的房间；
  两种模式对同一个房间并发采集会各建一个会话。
- **实测数据**：单路采集侧 28~38MB / 0.4~1.8% CPU，5 路并发 139MB / 3.1%，
  首音频约 0.7 秒，reflow 解析约 0.5 秒；详见 [docs/13](13-direct-capture-spike.md)。

### 内存实测（本机 16GB，Windows 10）

| 场景 | 浏览器 | 服务端 | 代理 | 合计 |
|---|---|---|---|---|
| 独立模式 3 路（按 0.93GB/路） | ~2.8GB | ~0.46GB | ~0.04GB | ~3.3GB |
| **共享模式 3 路（实测）** | **2.4GB** | 0.46GB | 0.04GB | **~2.9GB** |
| 独立模式 5 路（此前实测） | ~4.6GB | ~0.4GB | ~0.04GB | ~5.0GB |
| 共享模式 5 路（按每标签页边际 0.56GB 估算） | ~3.5GB | ~0.4GB | ~0.04GB | ~4.0GB |
| **direct 5 路（实测）** | **0** | ~0.46GB | ~0.18GB | **~0.64GB** |

共享模式省的是「每个房间一套浏览器基础进程」：浏览器主进程、GPU、网络、扩展控制页
这些固定开销只付一次；但每个抖音标签页本身仍要 400~560MB，所以 1 路反而更贵
（实测 1.3GB），2 路基本打平，3 路开始有净收益，5 路省得更多。想再省就删掉不听的房间，别让它们挂着。

direct 模式没有浏览器，采集侧只剩每路一个 ffmpeg（实测 28~38MB），5 路的代理 + ffmpeg
合计约 0.18GB；解析和分块都在代理里做，不再有 Chromium 的固定开销。

### 边界

- 共享浏览器整体崩了会带走所有共享房间；代理下一轮会把它们重新拉起，缺口按断流自愈处理。
- 所有房间共用一个浏览器配置目录（`data/profiles/shared`），不要拿它同时开别的用途。
- 共享模式仍是实验性选项，默认仍是 `per_room`。

## 一次性准备

```bash
pip install -r requirements-live.txt
python tools/fetch_models.py
python run.py
```

模型约 270MB，默认走 hf-mirror / gh-proxy，失败会自动回退官方地址；已经存在的文件会跳过。

## 使用步骤

1. 用 Chrome 或 Edge 打开 `http://127.0.0.1:8765/`（必须是 localhost，浏览器才允许采集标签页）。
2. 另一个标签页打开抖音直播并保持播放。
3. 点「● 实时监听」→「选择标签页并开始」。
4. 在弹窗里选中**抖音直播那个标签页**，确认左下角 **「分享标签页音频」已勾选**，点分享。
5. 页面会切成**监听工作台**（左边直播画面，右边实时字幕）。主播开口约 1 秒后先出现灰色「识别中」字幕，每 4 秒切句时替换成带说话人的定稿；两位说话人轮流发言时会自动分成「主播 / 嘉宾」。
6. 想放着不管时点右上「收起」，工作台缩成右下角的小胶囊（继续计时、继续转写），点「展开」回来。
7. 点「结束并保存」，本次场次会出现在顶部场次里，可以继续用时间轴、筛选、总结和「主播画像」。

## 场次切换

顶部左上角的场次按钮显示当前场次标题、时间和条数；点它展开面板：

- 按天分组（今天 / 昨天 / 具体日期），每行显示标题、时长、发言条数、采集方式，以及**有没有原始录音**。
- 顶部搜索框按标题或日期过滤；点空白处或 Esc 关闭。
- 选中某一场后，筛选、时间轴、总结和播放器都会切到该场。

网页地址里的 `?session=LIVE_2026…` 会跟着更新，可以直接收藏或分享某一场的链接。

**改名**：每行末尾 hover 出现 ✎，点开是改名弹层，里面有按内容给出的 2~3 个建议标题，
点一下填进输入框再改；顶部场次按钮也会同步。改名只动显示名，逐字稿、总结、导出内容都不变。

## 回看：音频回放

底部播放器是单实例的整场播放：

| 元素 | 说明 |
|---|---|
| ▶ / ⏸ | 播放 / 暂停；图标跟真实播放状态走（空格键同样有效） |
| 00:00 / 10:00 | 当前播放位置 / 整场时长 |
| 进度条 | 可拖动，拖动时只移动播放头，不会重复加载音频 |
| 1× | 播放速度，依次 1× → 1.25× → 1.5× → 2× |
| 点时间码 / 点发言 | 把播放头移到那一刻；总结里的「▶ 定位时段」会直接开始播放 |

顶部「⬇ 纪要 / ⬇ 字幕」导出本场：
- **纪要** = Markdown（场次信息 + 说话人统计 + 打点 + 逐字稿）
- **字幕** = SRT（带说话人前缀，可直接拖进剪辑软件）
导出内容只取数据库里的真实发言，不做二次加工。

音频由 `/api/audio` 带 `Range` 流式返回，浏览器按需取字节，拖动进度不会整段重下。
没有原始录音的场次（演示数据、尚未保存的场次）播放按钮是灰的，并给出提示。

## 全文稿：换一种读法（`/reader?session=…`）

按时间线的「发言记录」是一条一句，适合查证；想"读完一场"就用全文稿。顶栏「📖 阅读」新开一页：

| 元素 | 说明 |
|---|---|
| 分段 | 同一说话人连续发言合并成段；换人、静音超过 8 秒、或单段超过 320 字就断开 |
| 说话人 | 左侧色条 + 同色名字，颜色和时间轴、字幕一致 |
| 时间码 | 段首 `02:11–02:38`，默认隐藏，鼠标移上去才显示；**点段落直接跳到那一刻播放** |
| 筛选 | 上方说话人 chip 可多选（点掉谁就不看谁）；右侧「隐藏闲聊/广告」走 `value_tag=low` |
| 底部播放器 | 整场 WAV，拖进度条随意定位，空格播放/暂停 |
| 导出 | 顶部「⬇ 纪要 / ⬇ 字幕」导出当前这一场 |

底层是 `GET /api/reader` 返回的段落数组（`app/reader.py` 里做合并），不是前端临时拼的——
这样导出、打印、以后接 LLM 用的是同一套分段。

### AI 润色（原文不动）

逐字稿里有大量"呃""就是说""我我我"，还有被口水话打断的半截句子，读起来累。
阅读页顶栏的 **「✨ 润色本文」** 会让大模型**重写**每一段：删口水词、补全被打断的句子结构、
必要时调整语序和拆合句子，**只要意思不变**。不是只做删减——只删字的话，语法烂的地方还是烂的。

润完自动切到 **「对照」** 模式：每段两行——原文里删掉的字**标红加删除线**，润色里新增的字**标绿**，
段首挂 \`−N / +M 字\`，顶部给出全篇"共删 X 字、增 Y 字（删除率 Z%）"。

删除率高不代表坏：这本来就是"把口语改成书面语"的任务。真正要看的是**读得通不通**。

觉得上一版不理想（或换了模型）就点 **「重新润色」**，会强制重跑全部段落，不吃缓存。

**原文永远不改**：润色结果单独存 `polished` 表，只是显示层；导出和 SRT 仍然是原文。
鼠标悬停在润色后的段落上，会显示对应的原话。

| 项 | 说明 |
|---|---|
| 分批 | 8 段一次调用，按 id 返回；缺的段落自动回退原文 |
| 缓存 | 指纹 = 段落集合 + 模型名 + 提示词版本；任一项变了就重算，不会复用旧结果 |
| 护栏 | 长度必须在原文 35%~120% 之间：太短说明在概括（禁止），太长说明在加料（禁止）；数字/人名必须原样保留 |
| 失败 | 整场没有一段成功才报错；部分失败只影响那几段 |

**自动标题**：配了 `LIVENOTES_LLM_*` 时会给"内容型"标题（如「AI 培训陪跑 · 02:45」）；
没配时只能给"摘录型"——把原句洗掉口水词、截到句读，再拼上开始时间，另外附带
「N 人连麦 · 02:45」这种结构化备选。中文不切词做不出主题词，硬抽出来的是
"比如说""跟你讲"这类噪声，所以宁可不做。

## 文件中心（`/library`）

顶栏「🗂 文件中心」新开一页，管所有场次：

| 能力 | 说明 |
|---|---|
| 概览 | 场次数 / 录音总时长 / 音频占用 / 回收站条数 |
| 表格 | 标题、日期、时长、发言条数、录音大小；点表头排序，按标题或日期筛选 |
| 单条操作 | 阅读、播放、下载 WAV、改名、**只删录音**、删除 |
| 批量 | 勾选多场后：删除 / 只删录音 / 还原 / 彻底删除 |
| 回收站 | 删除是**软删除**：场次和音频一起移进 `data/trash/`，可还原，也可彻底删 |

**「只删录音」是重点**：WAV 是 115MB/小时，而价值几乎都在文字里。删掉音频，逐字稿、总结、
说话人、打点全都保留，只是不能回听了。

## 全局搜索（顶栏输入框）

搜的是**所有场次的逐字稿**，不是只看当前这场。输入两字以上即时搜索，结果按场次分组，
显示时间码、说话人、上下文，点一下跳到那一场并定位到那一刻播放。

实现上 >=3 字走 FTS5 trigram，两字词（比如「押金」）自动回退 LIKE——trigram 对两字词无效。

## 录完自动收尾

点「结束并保存」后，后台线程会顺手做两件事（不阻塞保存）：

1. **自动起标题**：还叫「抖音直播 2026/11/5 …」这种默认名时，用当前模型起一个（如「城市获客300元怎么分成 · 03:38」）；没配模型就退回摘录型标题。
2. **自动生成总结**：按「按内容」模式跑一次并存库，回看时直接有内容。

日志里能看到 `[live] 自动标题：…` 和 `[live] 已自动生成总结`。

## 实时异常提示

工作台会用人话提示三种现场问题：

| 现象 | 提示 |
|---|---|
| 连续 12 秒几乎没声音（RMS < 0.004） | 几乎收不到声音：检查标签页是否被静音、音量为 0 |
| 连续 60 秒没检测到人声 | 已经 N 秒没检测到人声：确认还在说话，或 BGM 盖过了人声 |
| 队列积压 / 丢帧 | 识别队列积压 N 句 / 音频积压已丢 N 块 |

## 跨场次主播画像

「主播画像」底部会额外统计**所有场次**里同标签说话人的表现：场次、总时长、语速、
每分钟提问数、口癖率。

注意它的边界：**按标签名对齐，不是声纹对齐**——同一场里改过名的会被算成两个人，
不同场里同名也不保证是同一个人。页面里也写了这句提示，不假装是精确的。

## AI 智能分类（可选，规则分类保留）

左侧「分类」标题行右侧有个 **「AI 分类」**：用大模型把这一场每句话重新判成五类之一
（实质讨论 / 上麦咨询 / 主持控场 / 闲聊 / 广告引流），并给一句 6 字以内的话题。

- **原来的规则分类不会被丢掉**：第一次跑 AI 时把规则结果快照进 `category_rule` / `value_tag_rule` 列，
  完成后在分类面板下方出现「还原规则分类」，一键回退，逐字精确还原。
- **花不花 token 由你决定**：只有点「AI 分类」才调用，且会先弹确认。
- **分片跑**：一次只处理 40 句，前端循环调用并在面板里显示「120/233 句」。
  这样单个请求只要十几秒，中途断了也能点「从断点继续」——已经处理过的不会再花钱重跑。
- 跑完在面板里显示：条数 · 模型 · 耗时 · tokens，跟总结的引擎条同一套口径。

放这一块的考虑：分类是**场次级属性**（属于这一场的内容结构），不是全局配置，所以不放设置里；
也不放总结 tab——总结是一次性产物，分类会长期影响筛选和总结范围。放在分类面板标题行，
改完立刻能看见 chip 上的数字变化，是唯一「所见即所得」的位置。

### 按分类：真正的按类分组

「按分类」不是换个筛选条件，而是把总结**按类别拆成几块**：每块一个类别标签（实质讨论 / 上麦咨询 / …）
和该类的发言条数，下面只放这个类别自己的要点。

分组走两条路，规则一致：

- 有模型：一次调用，要求模型按类别分组出点，**证据必须落在同一类别里**（不同类别的 id 会被丢弃）；
- 没模型：每个类别挑信息量最高的原句，最多 2 组要点。

## AI 分类的主题数（设置里可调）

之前每句话都让模型现编一个话题，一场下来能冒出上百个标签，等于没有分类。
现在改成**两阶段**：

1. 先让模型把整场归纳成 **恰好 N 个**主题（名词短语，≤6 字）；
2. 再让每句话往这 N 个里归，模型自创的主题会被就近塞回最像的那个。

N 在「⚙ 设置 → AI 分类 → 归纳成 N 个主题」里调，范围 3~40，默认 10。
这个偏好**跟连接档案无关**（存在 `settings.json` 的 `prefs` 里），换账号不会丢。

实测：193 句 → 8 个主题，分布 24~25 句/主题，没有长尾标签。

### 结束并保存：收尾状态机

点「结束并保存」不是在等一根 30 秒的保存进度条。**落盘本身约 1 秒**，重聚类、起标题、
生成总结都在后台跑，跑完自己会变绿——界面不再拿它们当「保存中」的进度条。

| 步骤 | 什么时候算完成 | 等不到时显示什么 |
|---|---|---|
| 录音落盘 | `/api/live/stop` 返回（此时数据已在库里，**关掉页面也不会丢**） | 失败才红，可「重试保存」 |
| 声纹重聚类 · 自动起标题 | 轮询到这一场的标题不再是默认名 | 「后台仍在跑」 |
| 生成总结 | 能读到这一场存下的 content 总结 | 「后台仍在跑」 |

`/api/live/stop` 一返回就弹「已保存 · N 句 · 时长」。后面两步只是弹窗里的两行状态，
轮询 90 秒仍没结果就写「后台仍在跑」——**不再用「跳过」糊弄**（以前打满 31.5 秒轮询上限，
就把还在跑的后台任务标成「跳过」，文案是假的）。

服务端收尾链路的保证（`app/live.py` 的 `_finalize_summary`）：

- 用整场声纹重聚类 → 一次模型调用同时拿总结和标题（省一遍 token）；
- 模型调用有**整次请求的硬上限** `LIVENOTES_LLM_TOTAL_TIMEOUT`（默认 75 秒）：
  socket timeout 只封单次读写，中转站慢吞吞吐字时永远不会触发，这条兜底是必须的；
- 模型超时/失败 → 落一条**本地抽取式总结**（0 token），界面那一步照样变绿；
- 每一步都写 `data/finalize.log`（终端也打印），带累计耗时——收尾跑在后台线程里，
  没日志时「后台没出东西」只能靠猜。

配套的保护：

- 再点一次「结束并保存」不会重复提交（`L.phase==='stopping'` 直接拦掉）；
- 暂停 / 打点 / 字幕 / 画面 / 全屏 / 结束按钮全部变灰不可点；
- 期间切场次、开新录音都会提示「上一场还在保存」；
- 关标签页会弹浏览器原生确认（`beforeunload`）；
- 保存失败给出「重试保存」，录音还在服务端临时目录，重试或下次启动自动捞回。

完成后弹「已保存 · N 句 · 时长」，两个按钮：查看这一场 / 关闭。关掉弹窗后后台轮询
还在跑，总结一落库就自动把逐字稿和总结面板刷成最新的（只在你仍停在这一场时才刷）。

## 时间轴对焦

点总结里的 **「▶ 定位时段」**（或点任意时间码、在记录里点一行）时，顶部时间轴会：

- 出现**蓝色播放头**，位置 = 时刻 / 总时长；
- 画出**对焦带**，覆盖该要点的时间区间（定位时段会带上原文的起止）；
- 把覆盖到的桶高亮（`.bucket.focus`），时间轴能横向滚动时自动滚进视野。

## 总结用哪个引擎

「AI 总结」右上角三档：

| 选项 | 行为 |
|---|---|
| **智能**（默认） | 内容够才调用大模型：**少于 15 条发言或少于 400 字，直接用本地抽取式**，0 token |
| 只用本地抽取 | 永远不调模型，要点 = 高权重原句组合 |
| 强制用大模型 | 不看体量，一定调（短录音想试模型时用） |

门槛在 `app/analysis.py` 里：`LLM_MIN_ROWS = 15`、`LLM_MIN_CHARS = 400`。

**什么时候才会真的调用模型**：只有点「生成总结」那一下。

| 动作 | 以前 | 现在 |
|---|---|---|
| 切换 tab（按内容/按时间段/按分类/当前筛选） | 每切一次都重新生成 | **只读**：先看本页缓存，再读库里存过的，都没有就显示「还没有生成过」＋一个生成按钮 |
| 切换场次 | 自动生成一次 | 读这一场存过的总结，不调模型 |
| 结束实时监听 | 前端再生成一次 | 等后台自动总结落库（最多轮询 7 秒），不重复烧 token |
| 改说话人/重新分人 | 自动重新生成 | 清缓存、重新读库（历史总结里的称呼是当时的快照，不会变） |

**生成时的交互**：

- 点了之后先跑一次 `/api/summarize/estimate`，告诉你「正在调用 deepseek-chat…（196 条发言）」还是
  「本地抽取中 · 9 条发言，不调用模型，0 token」；
- 面板里是转圈 + **实时计时**（0.1s 精度），能看见它在跑多久；
- 结果顶部有一条引擎条：
  - 蓝色 `大模型总结 · 模型名 · 3.2s · 1,690 tokens`（小圆点会呼吸，表示是模型产的）
  - 灰色 `本地抽取式 · 0 token · 内容太少（9 条 / 218 字），本次用本地抽取式，不消耗 token`
- 灰色条右侧有个 **「仍用大模型」**，一键强制重跑这次。

token 用量取自接口返回的 `usage` 字段，不是估算值；有的中转站不回这个字段，会显示「token 用量未知」。

### 实时字幕：改判「这句话是谁说的」

声纹聚类经常把一句话判错人。**点字幕里的说话人名字**，弹出当前说话人列表：

- 选一个人 → 只把这一句改判给他，其它句子不动；
- 选「＋ 新建说话人…」→ 起个名字，这一句归到新的人名下（自动分配 `SPK_xx`）。

改判是实时的：内存里的话轮比例（顶部那条彩色条和 chip 里的句数/时长）会立刻跟着重算，
数据库同步更新。已经录完的场次也能用同一接口改（`POST /api/utterances/reassign`）。

### 关于 Chrome 顶部的 Sharing 提示

开始采集后 Chrome 会在页面顶部显示一条：

- 这条提示的意思是：Chrome 正在把 **抖音标签页** 的画面/音频共享给 **我们的本地页面**，这是正常且正确的状态。
- **不要点「Share this tab instead」**——那会把共享源切换成我们的页面自己，转写会立刻变成静音。
- 想结束时点「Stop sharing」或工作台右下角的「结束并保存」，两者都会收尾并保存。
- 画面会直接嵌在工作台里（用的是同一个 video track），不需要另开窗口；音频只用于本地 ASR，画面是静音的，原标签页继续出声。

## 延迟与切句（为什么一开始出字很慢）

实时字幕的延迟 = **等 VAD 断句的时间** + **整句识别时间**，不是模型慢。

- SenseVoiceSmall-int8 在 CPU 上大约是 **0.04 倍实时**（10 秒音频约 0.4 秒算完），所以识别本身不是瓶颈。
- 原来的问题：VAD 要等到「连续静音 0.55 秒」才认为一句话结束。直播里一直有背景音乐/垫乐，VAD 会一直判定"还在说话"，于是一连几分钟不出句。实测出现过 **134 秒没有新句子**，界面上的「未转写」就是这么来的。
- 现在的做法：只要检测到人声，**每 4 秒强制切一刀**（`LIVENOTES_FORCE_SEGMENT_S`，默认 4）。这样字幕延迟有了上界：最慢约 4 秒 + 0.3 秒识别，平均 2 秒左右；队列实测不会积压（`queued=0`）。
- 想更快可以调小：`set LIVENOTES_FORCE_SEGMENT_S=2.5` 再启动。代价是句子更碎、声纹聚类更容易被短句带偏。
- 想文字更完整可以调大（6~8 秒），代价是最长要等 8 秒才出这一句。

面板上的三个数：**已转写**是真正送进 ASR 的人声时长，**人声**是 VAD 判定的说话时长，**静音**是没人说话的部分。它们不是"丢了"——静音本来就不会有字。

### 滚动字幕（默认开启）

当前这句还没到 4 秒切点时，服务端每秒把**已经收到的部分**先识别一次，面板底部显示一行浅色、斜体、带「识别中」标记的临时字幕；到切点后，这行消失，换成带说话人标签的定稿。

- 实测：开口后约 1.5 秒出现第一版灰字，之后约每秒变长；切点后约 0.3 秒定稿。
- 临时字幕**不写数据库**、不参与声纹聚类和总结，所以不会出现"半句话进了逐字稿"的问题。
- 临时字幕没有说话人：声纹需要整句（≥2 秒）才稳定，硬猜只会让标签来回跳。
- `LIVENOTES_PARTIAL_INTERVAL_S=0` 可关闭；调到 `0.6` 会更跟手，CPU 略增（实测整条链路仍远低于一个核）。

### 多路并发：ASR 工作池

以前每个会话一个采集线程，线程里直接调 `ENGINE.transcribe()`，而 transcribe 用一把
全局锁包住整个解码过程。10 路同时说话时，所有解码严格串行：一路的长句会拖慢所有路
的字幕；滚动字幕每秒一次解码，还会和更重要的定稿抢同一把锁。换更快的模型只能缩短
单次解码，解决不了这种队头阻塞。

现在拆成生产者和消费者（`app/asr_pool.py`）：

```
每路采集线程（VAD/断句） --submit--> 共享调度器 --dispatch--> N 个 ASR worker
```

- **识别器单例共享**：sherpa-onnx 官方明确 `OfflineRecognizer` 线程安全、`OfflineStream`
  不能跨线程共享；CPU provider 下多个线程各自 `create_stream()` 后并发 decode 即可。
  不复制 240MB 模型，内存只增加每个 worker 一个 28MB 的 CAM++ 声纹提取器。
- **定稿优先**：worker 先领定稿；临时字幕只在没有定稿排队/在跑时才解码。
- **同会话定稿串行**：声纹聚类和落库依赖顺序，所以一个会话同一时刻只跑一条定稿，
  其余按提交顺序排队；不同会话之间并行。
- **临时字幕合并 + TTL**：每会话最多一条在跑 + 一条待跑，新的覆盖旧的；切句/暂停
  会让旧结果整代作废；排队超过 `LIVENOTES_PARTIAL_TTL_S`（默认 2.5 秒）直接丢，
  下一帧本来就会覆盖更长的音频。
- **跨会话轮转 + 有界队列**：不会因为某一路持续说话饿死其他路；单会话定稿积压超过
  `LIVENOTES_ASR_MAX_PENDING_FINALS`（默认 8）丢最旧的一条并计入「未转写」，
  内存不会无限增长。
- **可观测**：`/api/live/status` 的 `asr` 字段和 `/api/live/info` 的 `asr` 字段直接给出
  排队数、丢句数、RTF、定稿/临时字幕的 P50/P95；压测脚本读同一份统计。

线程数默认按 CPU 核数自动决定（12 核 → 8 个 worker × 单次 4 个 intra-op 线程），
可以用 `LIVENOTES_ASR_WORKERS` / `LIVENOTES_ASR_THREADS` 覆盖。压测方法和实测数据见
[`docs/07-asr-concurrency.md`](07-asr-concurrency.md)。

## 已知边界

- **2~6 人轮流说话可用**：实时阶段的在线聚类上限是 8 人（`LIVENOTES_MAX_SPEAKERS`），但
  实时只能力求“这一句像谁”，真正准的人数由结束后的全场重聚类决定。抢话/重叠段仍可能归错，
  左侧「身份校正」可以改名，或直接点「重新分人」。
- **背景音乐**会影响断句和识别；BGM 很大时会把音乐当人声。
- **不是逐字流式 ASR**：临时字幕每秒整段重识别，会整行替换，不会像云端流式那样逐字追加；定稿仍是 4 秒一小句。好处是已进逐字稿的文字不会反复改写。
- **必须用标签页**：选整个屏幕/窗口也能工作，但会把系统声音带进来。
- **画面是"镜像"不是嵌入网页**：抖音页面有 `X-Frame-Options`/跨域限制，不能用 iframe 直接嵌；这里是把标签页画面通过 `getDisplayMedia` 显示出来，效果一样，且不用 Electron/WebView。
- 录到的音频保存在 `data/audio/LIVE_*.wav`，可在底部播放器回放；逐字稿在 SQLite 里。
- 只适合本地/自有设备上的复盘分析；录他人直播涉及个人信息，不要公开传播或商用。

## 说话人：实时在线聚类 + 结束后重聚类

实时链路必须“来一句判一句”，只能拿固定阈值跟已有簇比，因此有两个天生缺陷：第 4 个人开口时
会被静默并进最近的那个人；BGM 把整场相似度压低后，固定阈值也没法自适应。所以这里做两层：

| 阶段 | 做什么 | 依据 |
|---|---|---|
| 采集时 | 在线贪心聚类，只为实时字幕先给个标签；每句的 192 维声纹同时存进 `utterance_emb`（float16，约 384 字节/句） | 阈值 0.45，最多 8 簇，短于 1.2 秒不新开簇 |
| 点「结束并保存」时 | 用整场声纹重跑球面 k-means，轮廓系数自动选 K，改写全场 `speaker_id` 与标签 | 见 `app/recluster.py` |
| 回看时 | 左侧「重新分人」可再跑一次，也能手动指定 2/3/4/5/6/8 人 | `POST /api/speakers/recluster` |

要点：

- **自动判断人数**默认按轮廓系数在 2~10 之间选，分数接近时偏向更少的簇（宁可少分一个，也不要把一个人拆成两个“嘉宾”）。
- 只有 1~2 句的小簇会被并回最近的大簇——那是 BGM 和抢话噪声，不是人。
- 你已经改过的昵称会被继承：一个旧昵称只会落到“覆盖它成员最多”的那一个新簇上，不会出现两个都叫「嘉宾1」的人；其余按发言时长重新编号，话最多的那个记作「主播」。
- 声纹表只存向量不存音频，一场 500 句约 190KB；旧场次可用 `python tools/backfill_embeddings.py` 从已有 WAV 补出来（没有录音的场次补不了）。
- 重聚类只改说话人，不动逐字稿文字和已有总结；早先保存的总结里的称呼是当时的快照。

## 排错

| 现象 | 处理 |
|---|---|
| 弹窗里没有「分享标签页音频」 | 必须选「标签页」，不能选窗口；Chrome/Edge 版本过旧 |
| 页面提示模型未就绪 | 运行 `python tools/fetch_models.py` |
| 提示不支持采集 | 用 `http://127.0.0.1:8765/` 打开，不要用局域网 IP |
| 一直不出字 | 看「实时监听」面板底部的错误；确认标签页仍在播放、音量不为 0 |
| 说话人全变成同一个人 | 主播与嘉宾音色太接近，或单句太短；点「重新分人」手动指定人数 |
| 「重新分人」提示没有声纹 | 该场次是加声纹存盘之前采的，先跑 `python tools/backfill_embeddings.py`（需要原始录音） |
| 分出来的人比现场多 | 现场有 BGM/回声被当成新人；选「3 人」这类固定 K 再跑一次 |
