# 07 · AI 总结与 AI 分类：合并，还是分开

> **结论先行**：该合的是**入口、编排、缓存**，不该合的是**一次模型调用**。
>
> 推荐 **C 方案**：右栏只留一个「AI 分析」，服务端跑两段流水线——**理解段 1 次调用**（标题 / 备选名 / 概述 / 主题词表 / 主讲人），**标注段 1~2 次调用**（用理解段定下的封闭主题集给每句打类别），最后**本地 0 次调用**重算统计与「按分类」视图。
>
> 实测一场 321 句的场次：现在走完全套要 **≈ 47,000 token / 11 次请求 / 约 1.5 分钟**；C 方案约 **15,000 token / 2 次请求 / 25 秒**。**token 打三折、往返打两折**，且标题、主题、标签三者天然一致。
>
> 但**先做第 0 步**（编码瘦身 + 结果复用，约 1 人天）：它不改任何产品逻辑，就能把最大的那笔浪费砍掉一半，也是后面合并的地基。

## 1 现状：一次"AI 分析"被拆成了三个入口、三套词表

| # | 入口 | 代码 | 调几次模型 | 产物 | 缓存 |
|---|---|---|---|---|---|
| 1 | 右栏「生成总结」 | `analysis.make_summary` `app/analysis.py:434` → `_llm_points` `:370` | **1 次** | 概述 + 要点 + 标题 + 备选名 | 按 `(session_id, scope)` 存最新一条，**无指纹** |
| 2 | 左栏「AI 分类」 | `classify.ai_classify` `app/classify.py:95` | **1 次提主题 + ⌈N/40⌉ 次打标**（321 句 = 10 次） | 每句 `category` + `topic` | **无**，重跑即全量重算 |
| 3 | 「换一个」标题 | `titles.llm_title` `app/titles.py:140` | 1 次 | 单个标题 | 无 |

三套词表互不知情：

- 总结自己按 `topic` 分组、自己起名（`analysis.py:347 _LLM_PROMPT`）；
- 分类自己 `_propose_topics` 归纳 10 个主题（`classify.py:73`，`settings.prefs()["topics"]`）；
- 规则分类还有一套 `TOPIC_RULES` 关键词表（`analysis.py:39`）。

**难看的现状是"半融合"**：总结的 prompt 已经把每句的 `category`、`topic`、`speaker` 一起喂给模型（`analysis.py:384-386`），也就是说**总结一直在吃标签**——但标签要靠另一个按钮生产。没点过那个按钮的场次，总结分组吃到的是关键词规则的结果。

这台机器上的 22 场真实录音里，只有 3 场跑过 AI 分类（都是最近几场）。样本太小，不足以下产品结论，但至少说明：**一个决定总结质量的前置步骤，藏在左栏一个 11px 的链接里，实际很难被想起来点。**

还有两个细节让状态更糊：`store.has_ai_categories`（`app/store.py:694`）写了但**没有任何调用方**——UI 层根本没法回答"当前这批分类是规则还是模型给的"；`classify.MAX_ROWS = 2000`（`classify.py:18`）也是定义了没用上。

## 2 实测账本（真实场次，ID 已脱敏）

数据库里 `summaries.payload_json.usage` 留了真实 token 数：

| 动作 | 调用数 | prompt | completion | 合计 | 耗时 |
|---|---|---|---|---|---|
| 生成总结（按内容） | 1 | 22,339 | 598 | **22,937** | **15.9 s** |
| 提主题（分类第一片） | 1 | ~2,289 | — | ~2,300 | ~5 s |
| 打标（9 片 × 40 句） | 9 | ~10,533 | ~11,166 | ~21,700 | ~40–70 s（估） |
| **当前总计** | **11** | | | **≈ 47,000** | **≈ 1.5 min** |

同一场次原文只有 **6,071 个字符**（321 句，平均 18.9 字/句）。也就是说，为了理解 6k 字的对话，我们付出了 47k token。

## 3 真正的浪费不在"多一次请求"，在三个地方

用户直觉「分类多调一次模型很浪费」方向是对的，但把账拆开，主因不是请求数：

**(1) 每行 JSON 信封是正文的近 4 倍。**
总结的 user payload 实际序列化出来是 **38,554 字符**，其中原文只占 6,071（**15.7%**）。剩下 84% 是 `{"id":123,"t":12.3,"speaker":"阿哲","category":"substantive","topic":"综合/未归类","text":"..."}` 这种每行固定 40~50 token 的壳子。321 行 × 50 ≈ 16k token 纯壳子。

→ 同一份内容换成**位置数组 + 说话人索引 + 类别短码**，实测 **38,554 → 13,168 字符（−66%）**。这一条不花任何产品设计成本。

**(2) 同一段对话被完整读了 3 遍。** 总结读一遍（22k）、提主题读 1/3 遍（2.3k）、打标又读一遍（10.5k）。合并后至少省掉一整遍。

**(3) 没有指纹，重算即重花。** `store.save_summary`（`store.py:910`）每次都是 INSERT，`latest_summary` 只按 scope 取最新一条。同一场次里连点两次「生成总结」，就是两个 22k；分类更是全量覆盖重打标。润色那边已经做了 `_fingerprint`（`polish.py:45`，段落集合 + 模型 + 提示词版本），总结和分类都没有。

**这三条加起来，才是"浪费上下文"的真相**：不是 11 次请求贵，是每次请求都在为同一份文本的壳子和重复阅读付钱。

---

## 4 "半融合"比"不融合"更贵

| 症状 | 后果 |
|---|---|
| 总结吃标签，标签靠另一个按钮 | 用户以为点了总结就完整了，实际分组用的是规则分类 |
| 两套主题词表 | 总结里说"短视频与直播"，分类里可能冒出"抖音起号"，同一场两个主题体系 |
| 标签写回 `utterances.category/value_tag` | 改的不只是标签：筛选计数、`importance`、低价值剔除、覆盖率、高光打分全都跟着变 |
| 无指纹 | 现场直播还在追加句子，重算一次就是全量重算 |

结论：**融合是对的，但融合点选在"数据写回"这条链上，风险也在这条链上。**

## 5 三个方案

| # | 方案 | 调用数 | token | 失败面 | 长场次（>600 句） | 一致性 |
|---|---|---|---|---|---|---|
| A | 维持现状 | 11 | 47k | 分片可续 | 可以 | 差（三套词表） |
| B | **一次调用全做**（标题+概述+要点+321 行标签塞一个 JSON） | 1 | ~25k | **全有或全无** | **撑不住**，只能截断 | 最好 |
| C | **一次入口 + 两段流水线 + 紧凑编码** | 2 | ~15k | 分段可续、可部分成功 | 可以（标注段分片） | 好（主题闭集共享） |

**B 看起来最省，实际是最脆的**：

- 输出要从 598 token 涨到 3,000~11,000 token，JSON 截断概率随行数线性上升；一旦断在半截，标签和总结一起丢。
- 让模型"边标注 300 行边写长文概述"，长文质量通常下降——标注是压缩任务，概述是抽象任务，放在一个 completion 里会互相稀释注意力。
- 2000 行上限的场次（`classify.py` 里的 `MAX_ROWS`、`query_utterances limit=20000`）根本塞不进一次调用，最终还是得分片——那 B 就退化成了 C，只是失败面更差。

**所以 B 只适合"短场次 + 用户明确选了极致省钱"这一个角落**，不该做默认路径。

## 6 推荐：C 方案的两段流水线

### 6.1 新增一张 job 表

```sql
CREATE TABLE analysis_runs(
  id TEXT PRIMARY KEY,          -- run_xxx
  session_id TEXT, stage TEXT,  -- understand | label | rollup
  status TEXT,                  -- queued | running | done | failed | partial
  progress INTEGER, total INTEGER,
  fingerprint TEXT,             -- rows_hash + prompt_version + model
  usage_json TEXT, error TEXT,
  started_at TEXT, finished_at TEXT
);
```

一个 run 一次点击，UI 只认这个 run 的进度。现在的"前端 while 循环 + 断点续传"（`index.html:1247 classifyLoop`）保留能力，但搬到服务端，关页面不中断。

### 6.2 三段职责

**P1 理解段（1 次调用，输入是采样不是全文）**
均匀采 150~200 句 + 本地统计（时长、说话人时长占比、冷场、覆盖率），一次产出：

```json
{"title":"…","title_alts":["…","…"],"overview":"…",
 "topics":["空军直播获客","商业认知",…],        // 6~10 个，封闭词表
 "host_speaker":"SPK_00",
 "speaker_roles":{"SPK_00":"主讲/主播","SPK_01":"提问嘉宾"}}
```

采样而不是全文，是因为起名和概述要的是**覆盖面**，不是逐句覆盖。这一步比现在的 `_llm_points` 更省，还多拿到说话人角色（现在 `coach.py` 只能靠正则猜主播）。

**P2 标注段（每片 ≤200 句，通常 1~2 次）**
主题集来自 P1，**不再自己提主题**；输出紧凑：

```json
{"items":[[12,1,3],[13,1,3],[14,2,0]]}   // [id, 类别码, 主题下标]
```

类别码 1~5 映射五个类，主题只给下标——输出 token 从每行 ~35 降到 ~6。

**P3 汇总（0 次调用）**
用 P2 的标签在本地重算：五类计数、`value_tag`、`topic_tally`、覆盖率、`importance`；「按分类」tab 的分组结构直接由标签生成，不再需要 `_llm_groups` 的那次额外调用（要写要点时才点一次，或直接用 P1 的 overview + 每组抽取式要点）。

### 6.3 紧凑编码统一用在所有 LLM 入口

```
现在  {"id":123,"t":12.3,"speaker":"阿哲","category":"substantive","topic":"综合/未归类","text":"…"}
之后  {"spk":["阿哲","嘉宾1"],"cat":{"1":"substantive"},"u":[[123,12.3,0,1,"…"]]}
```
实测 38,554 → 13,168 字符。总结、分类、润色三处都能用，收益一次性落袋。

### 6.4 增量与指纹

- 标注段按 `utterances.id` 记 `labeled_fingerprint`；直播追加的新句只标新增部分，老句不动。
- 总结用 `(rows_hash, prompt_version, model)` 做 key：文本没变、模型没换、提示词没改 → 直接返回上一次结果，**0 token**。
- `prompt_version` 已经在 `classify.py:21`、`polish.py:22` 有先例，照抄即可。

### 6.5 失败语义（比现在更宽松，不是更严）

| 失败点 | 现在的行为 | C 方案的行为 |
|---|---|---|
| P2 第 2 片超时 | 提示"从断点继续"，用户得回来点 | job 自动重试 1 次；失败则**已标注的片照常入库**，标记 `partial` |
| P1 超时 | 标题退化成 `structural()` 人数标题 | 标签照常写、分类照常可用；标题只出候选不覆盖正式名 |
| 全挂 | 提示失败 | 回退本地抽取式，caveat 里写清"这次没调模型" |

**标签写回仍然保留 `category_rule` 快照 + 一键还原**（`store.py:669/686`）——这条不能丢，它是"模型可能更玄"的兜底，也是这个项目一贯的诚实边界。

### 6.6 UI 上怎么收

- 右栏顶部一个主按钮：**「AI 分析」**，旁边一个档位选择：`轻（只要总结）` / `全（总结+标签，多约 8 秒）`。
- 左栏「AI 分类」不删，改成二级动作 **「重新标注」**，文案改成"整场重打一次标签（通常不需要）"。
- 生成前给一行成本预估：`预计 2 次请求 · 约 1.5 万 token · 25 秒`（`/api/summarize/estimate` 已有雏形，扩成 job 预估）。
- 分类区加一个状态徽标：`规则分类` / `AI 标注 · 17:20`——顺手把 `has_ai_categories` 这个死函数用起来。

## 7 明确不做的三件事

1. **不做"打开场次就自动分析"**。项目现在"不会自动调用模型"的约定是对的，改成自动会让每次翻场次都烧钱，也会让"这个名字是谁起的"重新变糊（`titles.apply_summary` 的五种归属就是为这个存在的）。
2. **不做"一次 JSON 既标 300 行又出长文"**。见第 5 节 B 方案。
3. **不做"标签不可逆覆盖"**。快照 + 还原必须留着。

## 8 落地顺序与验收

| 步 | 内容 | 工作量 | 可验收的硬指标 |
|---|---|---|---|
| **0** | 紧凑编码（三处 LLM 入口）+ 总结指纹 + 分类增量 | 0.5–1 人天 | 同一场连点两次总结，第二次 **0 token**；总结 payload 字符数 **−60%**；追加新句后重跑分类，只标新增行 |
| **1** | `analysis_runs` + 统一入口「AI 分析」+ 服务端进度 | 1–2 人天 | 关掉页面再回来，进度还在；失败能续 |
| **2** | P1/P2 编排 + 主题闭集共享 + 「按分类」免调用 | 1 人天 | 321 句场次一次点击 = **≤2 次请求、≤16k token、≤30s**；标题/主题/标签三者一致 |

**总验收口径（拿截图那场跑）**：总 token 从 ≈47k 降到 ≈15k；请求数 11 → 2；耗时 ≈90s → ≈25s；`按分类` 里五个类的计数与左栏筛选计数**逐项相等**（今天两边可以不等，因为一个吃规则标签、一个吃 AI 标签）。

## 9 风险

| 风险 | 概率 | 缓解 |
|---|---|---|
| 紧凑编码让模型看不懂、漏行变多 | 中 | 先在一场真实数据上 A/B，比对 `changed` 行数与人工抽检 20 行；不行就只对 user payload 压缩，保留 key 名 |
| 两段之间主题不一致（P2 自创主题） | 中 | 主题只允许下标；越界就丢进"最相近"并记 `off_topic` 计数，超 5% 报警 |
| 合并后单次点击更慢（2 次串行 vs 1 次） | 低 | P1 只有采样，通常 5~8s；且 UI 首屏可以先出标题和概述，标签进度条后到 |
| 标签写回影响高光/覆盖率等下游 | 中 | 写回后重算一次派生字段（已有 `recluster`/`highlight` 的重算入口），并在改动最多的场次上回归 |

---

**一句话给决策**：这不是"省一次请求"的问题，是"同一份内容我们已经用三套词表读了三遍"的问题。**统一入口、统一词表、统一缓存，但保留分片和可回退**——花 3 人天，换来 token 打三折、交互从"两个按钮等两次"变成"一次点击看进度"，外加标题与分类终于说的是同一件事。

### 实测（库副本 + 假模型，走真实 HTTP 链路，不联网不花钱）

| 项 | 改前 | 改后 |
|---|---|---|
| 321 句场次的总结 payload | 38,554 字符 | **12,968 字符（−66%）** |
| 连点两次「生成总结」 | 22,937 × 2 token | 第二次 **0 token** |
| 分类重跑（没有新增句子） | 10 次调用 / ≈24k token | **0 次调用** |
| 直播追加 3 句后重跑分类 | 重标全 321 句 | **只标 3 句 / 1 次调用** |
| 主题集 | 每次重新归纳 | 落库复用，`force` 才换 |
| 还原规则分类后再点 AI 分类 | 全部跳过（"没反应"） | 正常从头标 |

### 怎么验（人工，3 分钟）

1. 打开任意一场，点两次「生成总结」——第二次技术条应显示 `缓存命中 · 0 token`。
2. 左栏「分类」区应显示 `已 AI 标注 n/N 句 · M 个主题`；点「AI 分类」只补未标句，`全部重标` 才整场重来。
3. 点「还原规则分类」，再点「AI 分类」——应该能重新标，而不是没反应。
4. 改一句分类（或跑一次分类）后再总结——缓存应失效并重新调用，说明指纹把标签算进去了。

### 仍需重启

后端是 `app/*.py`，`python run.py --reload` 会自动换进程；直接 `python run.py` 的话需要手动重启一次。
前端 `index.html` 每次请求都读磁盘，F5 即可。

### 还没做（第 1/2 步）

统一入口「AI 分析」、`analysis_runs` job 表与进度、P1 理解段 / P2 标注段的两段编排、以及把主题闭集共享给总结。**第 0 步的指纹与增量正是它们的前置条件**：没有指纹，合并后"一次分析"无法判断该不该重跑；没有增量，长场次每次合并都要全量重标。

## 11 · 第 1 步已落地：统一入口 + job 表 + 服务端进度（2026-11-05）

| `app/web/index.html` | 「AI 分析」主按钮 + 进度条（阶段 / 百分比 / 取消）＋ 刷新后 `resumeRun()` 接上进度；原「生成总结」降为按当前维度生成 |

### 一个关键顺序决定：先标注，再总结

第 0 步结束时发现：如果先总结后标注，总结吃到的是**规则标签**，标注一跑完这份总结就过期了——
这正是"两个按钮各跑各的"留下的坑，合并了入口却不解决顺序，等于把坑埋进流水线。

所以 `STAGES["full"] = [label, summary]`。好处是连锁的：

- 总结吃的是标注后的 `category/topic`，"按分类"视图与左栏计数天然一致；
- 第二次点「AI 分析」时标签没变、总结指纹命中 → **整条任务 0 token**（实测 11 次调用 → 0 次）。

### 实测（库副本 + 慢速假模型，走真实 HTTP）

| 场景 | 结果 |
|---|---|
| 321 句首次全量 | 11 次调用（提主题 1 + 注 9 + 总结 1），两段都 done，321/321 已标 |
| 同一场再点一次 | **0 次调用**，总结显示「缓存命中 · 0 token」，任务 1 秒内 done |
| 397 句跑到 120 句时取消 | `canceled`，已标 120/397 **保留**，无残留线程，后续可继续 |
| 取消后重新发起 | 8 次调用补完剩余 277 句 + 总结，最终 397/397 |
| 同一场连点两次 | 第二次直接返回同一条 run（`already=true`），不会排队第二条 |
| 模型未配置 | `start` 直接 400，不建空任务 |

顺带修掉一个只有并发才会暴露的 bug：`analysis_runs` 用 `created_at`（秒级）排序，
同一秒内连跑两条会选错 run，前端拿着上一条的进度画进度条 —— 改成按 `rowid` 排序。

### 还没做（第 2 步）

现在两段还是"背靠背调两个老函数"：总结自己采样、分类自己提主题，主题集仍是分类自己的那套。
第 2 步把 P1（理解：标题/概述/主题/主讲人）抽出来做成独立一次调用，分类只在 P1 的主题闭集里选，
总结复用 P1 的概述 —— 那时才真正是"一份内容、一套词表、一遍读懂"。

## 12 · 第 2 步已落地：P1 理解 / P2 闭集标注 / P3 本地汇总（2026-11-05）

一次「AI 分析」现在的调用账：**321 句的场次 = 3 次调用**（原来 11 次）。

### P1 理解段（1 次调用）

`analysis._llm_points` 升级成"理解整场"：一次产出**标题 + 备选名 + 概述 + 要点 + 主题词表 + 主讲人**。
两处关键改动：

- 输入**去掉了逐句 category/topic**（`_pack_rows(..., with_cat=False)`）。这一步跑在标注之前，
  那时的类别还是关键词规则给的，喂给模型既占 token 又误导它；去掉后 270 行只有 11,215 字符。
- 输出的 `topics`（6~10 个、每个 ≤6 字）落进 `sessions.ai_topics_json`，成为后面标注的**闭集**。

落库有护栏：只有这场**还没标过任何句子**才写。否则用户点一下总结，主题换了，
全场 `ai_fp` 失效、下次整场重标——这个代价没人愿意付。

### P2 标注段（1~2 次调用）

- 主题只许从 P1 的词表里选，输出改成紧凑三元组：`{"items":[[id, 类别代号, 主题下标]]}`
  （`1 实质 / 2 咨询 / 3 控场 / 4 闲聊 / 5 广告`）。输出 token 从每行 ~35 降到 ~6。
- 批大小 40 → 200：321 句 2 次调用，2000 句 10 次。
- 没有现成词表时才自己归纳一次兜底（`_propose_topics` 仍保留）。
- 解析兼容旧格式（模型/中转站不听话时返回 `{"id","category","topic"}` 也不会整场作废）。

### P3 汇总段（0 次调用）

`analysis.finalize()`：

- 按 id 重新取证据，**刷新证据里的类别/主题快照**（否则会出现"左边筛选说是广告、右边证据写着实质讨论"）；
- 重算 stats / coverage / 说话人；
- **给总结换一个新指纹**——这是关键：P1 跑在标注之前，指纹是按旧标签算的，
  不换的话标完再点「生成总结」会判定过期，白烧一遍模型。

「按分类」视图同样改成 0 调用（`_label_groups`）：分组来自标签、标题带主导主题
（如「实质讨论 · 直播获客」）、证据是原句。要模型写的文案，显式选「强制用大模型」才走 `_llm_groups`。

### 实测（库副本 + 假模型，走真实 HTTP）

| 项 | 第 1 步 | 第 2 步 |
|---|---|---|
| 321 句首次全量 | 11 次调用 | **3 次**（理解 1 + 标注 2 + 汇总 0） |
| P1 输入体积（270 行） | 13,168 字符（带 cat/top） | **11,215 字符** |
| 标注输出 | 每行 ~35 token | **每行 ~6 token** |
| 主题来源 | 分类自己提（另 1 次调用） | P1 词表，**0 次额外调用** |
| 「按分类」tab | 1 次调用（`_llm_groups`） | **0 次**，本地按标签汇总 |
| 再点一次「AI 分析」 | 0 次 | **0 次**（三段全部命中：缓存 + 无脏行 + 本地汇总） |
| 标注与总结的一致性 | 两套词表 | 同一套词表；证据快照随标签刷新 |

### 还剩什么

- `_llm_groups` 只在「强制用大模型」时用得上，可以视作"要点文案"的付费选项，不是默认路径。
- 分类的 `PROMPT_VERSION` 已升到 v2：老标签会在下次标注时自动重标一遍（一次性成本，符合预期）。
- 真正要盯的是**模型对紧凑输出和闭集主题的服从度**：`_parse_items` 已经把"写成对象""漏 id""主题越界"都做了兜底，
  但真实模型上的漏行率、主题漂移率还得拿几场真数据看。建议下一轮用真实模型跑 3 场，记录 `changed` 与人工抽检 20 行。
