# 开发模式：改代码自动重启（但不打断录制）

## 怎么用

```bash
python run.py --reload
```

等价于 `python tools/dev.py`。它会用一个守护进程托管真正的服务（`run.py`），监视
`app/**/*.py`、`tools/*.py`、`run.py` 的改动。

## 三种情况的行为

| 你保存代码时… | 守护进程的动作 | 你会看到 |
|---|---|---|
| 没在采集 | 立刻重启，约 1 秒 | 页面刷新一下就是新代码 |
| 正在「实时监听」 | **不重启**，记一条待重启；这场结束后自动换代码 | 录制不受影响，字幕继续出 |
| 改出了语法错误 | 新进程起不来，守护进程不退；改好再保存就自动拉起 | 控制台会指出哪一次改动失败 |

判断「在不在录」用的是 `GET /api/live/info` 里的 `active` 列表：只要有一场
`running=true`（暂停中也算），就不重启。

## 为什么不是 importlib.reload

实时链路里有一个常驻 worker 线程、一个已打开的 silero VAD 实例和两个 ONNX 会话。
reload 只替换模块对象，管不到这些已经存在的旧对象，结果是「代码看着是新的、跑的还是旧的」，
比直接重启更难查。所以这里是换进程，不是换模块。

## 探测失败不等于空闲

守护进程靠 `GET /api/live/info` 判断有没有在录。**探针超时不能当成"没在录"**——
服务正在跑 ASR 或长模型请求时，1.5 秒的探针很容易超时，一旦误判成空闲就重启，
正在处理的请求会当场被掐断（前端看到 `Failed to fetch`），录制也会断。

现在的规则：探针超时 **5 秒**；失败返回「未知」，遇到未知**一律不重启**，等下一轮再问。

## 端口守卫

Windows 上 `SO_REUSEADDR` 允许两个进程绑同一个端口，请求随机落到其中一个，
表现成「页面时好时坏」。现在两处都拦住了：

- `make_server()` 先用不带 REUSEADDR 的裸 socket 探一下，被占用就直接报错退出；
- `tools/dev.py` 启动前也探一次，发现已有服务在跑就拒绝启动（退出码 2）。

## 其它

- **前端不用重启**：`app/web/index.html` 每次请求都从磁盘读，改完按 F5 就是新的。
- **数据不会丢**：重启只换进程，SQLite 文件一直在；正在录的场次因为要等它结束，不会被截断。
- **想立刻生效**：不想等这场录完，就点「结束并保存」，代码下一秒自动换上去。
