## 0. 结论先行

当前问题的本质不是「窗口开在哪儿」，而是三套模型叠在了一起：

1. **页面模型**：功能 = 页面，切页面 = 整页刷新（`location.href='/?session='`）。
2. **浏览器模型**：`window.open` = 新窗口，窗口里再套标签栏 + 地址栏。
3. **录音模型**：采集在另一套浏览器视图/进程里跑，主窗口看不见。

三者叠加，就有了现在的三层界面：主窗口网页顶栏 → 应用内浏览器标签栏/地址栏 → 收听页自己的顶栏。用户看到的是「一个 App 里又装了一个浏览器，浏览器里又装了一个网站」。

**建议：以方案 B（单窗口工作区）为目标，用方案 A 的壳作为第一阶段，把方案 C 的「页面按需显示」作为增强项。**

理由：

- 不换壳（继续 Tauri 2）、不重写引擎、不推翻现有采集链路；
- 保留收听页已经做得不错的监控墙、波形、诊断语言；
- 一次解决「弹窗」和「录音状态不可见」两个根问题；
- 布局为 5 路监控和未来多屏留出位置；
- 迁移可以分四步走，每步都能独立上线。

**不推荐迁移 Electron**：现有 5 路浏览器采集约 4.6GB，本机 16GB（另有 WSL 4GB），再叠一个 Chromium 壳会把余量吃光；且 [docs/20](20-tauri-2-adr.md) 已对 Tauri 2 做过决策。Electron 的 `<webview>` 能解决原生视图叠加问题，但代价和收益不成比例。

## 1. 现状诊断

### 1.1 现在的一次「收听」

```
主窗口（工作台）
  └─ 点击「🎧 收听」
       └─ window.open('/rooms')                         ← main.js:148
            └─ Tauri on_new_window 拦截                   ← lib.rs:on_new_window
                 └─ 打开第二个窗口「LiveNotes · 应用内浏览器」
                      ├─ 标签栏（LiveNotes · 浏览器 / 收听）
                      ├─ 地址栏 + 前进后退 + 静音 + 字幕 + 停止
                      ├─ 状态栏
                      └─ 页面内容：/rooms
                           └─ 自己还有一层「直播语记 / 工作台 / 收听 / …」顶栏
```

一次点击之后，用户要面对：一个新窗口、两层导航、一个地址栏、一个和主窗口互不相干的录音状态。

### 1.2 六个具体问题

| # | 问题 | 证据 |
|---|---|---|
| 1 | **两个窗口、三层 chrome** | 主窗口顶栏 + 浏览器窗口的标签/地址栏 + 收听页顶栏 |
| 2 | **导航靠开新窗口** | 收听/文件中心/人物/阅读/高光榜全是 `window.open(..., '_blank')`（`app/web/js/index/main.js:142-150`） |
| 3 | **录音状态在窗口之外** | 主窗口没有「正在录几路、哪路断了」；只有托盘和另一个窗口知道 |
| 4 | **整页刷新，状态丢失** | 切场次 `location.href='/?session='`；筛选、滚动、播放位置全部重建 |
| 5 | **两套视觉语言** | 工作台浅色蓝调（`index.css`），收听页深色信号调（`rooms.css`），浏览器窗口又是浅色 |
| 6 | **信息架构按页面而不是按对象** | 用户心智是「这一路直播 / 这一场录音」，界面却是「收听页 / 阅读页 / 高光页」 |

第 3 条最值得警惕。收听页底部要写一句「**关掉这个页面不影响录音**」——需要向用户解释「页面」和「录音」不是一回事，本身就是设计债的语言证据。

### 1.3 现有资产（不要推翻）

- 收听页的**房间卡片、波形、状态分级（在听/异常/启动中/已停止）、诊断文案**，已经是产品里最有辨识度的部分。
- 原生 WebView2 + `captureStream()` + PCM 回传链路（`rooms.rs`）稳定，方案里不动。
- 托盘、诊断包、引擎守护、单实例，继续保留。
- 现有 URL（`/`、`/rooms`、`/reader?session=`）可以保留为深链，只是不再用「新窗口」打开。

## 2. 设计目标与原则

**一句话目标**：打开 LiveNotes 之后，用户只需要面对**一个窗口、一个对象列表、一个主画布**；录音是常驻状态，不是某个页面的局部状态。

### 六条原则

1. **单窗口**：所有主流程在主窗口完成。新窗口只留给「登录 / 支付 / 外部链接」这类必须离开产品的操作。
2. **对象优先于页面**：房间（直播）、场次（录音）、人物是第一等公民；页面只是对象上的视图。
3. **采集是常驻状态**：正在录几路、哪路异常、ASR 是否延迟，在窗口里始终可见、可操作。
4. **切换不中断**：换视图不停采集、不丢筛选、不丢播放位置；切回来是原样。
5. **分屏而非浮层**：原生 WebView2 是子窗口，盖不住也裁不了；需要面板时**挤占布局**，不要覆盖。
6. **一套语言**：一套 token、一个强调色、一种密度；深色信号语言作为产品识别。

### 非目标

- 不重写 Engine / ASR / 总结链路；
- 不删除网页版（`python run.py`）；桌面端先落地，网页版后续共享壳；
- 不在第一阶段做完整视觉改版（只统一 token 和外壳）；
- 不为了「像 Claude」而牺牲直播场景的密度和专业性。

## 3. 三套方案

### 3.1 方案 A · 单窗口标签式（Browser-style）

**一句话**：保留现有所有页面，在主窗口里做一个像 VS Code / Codex 的标签系统；收听页、阅读页、文件中心都变成主窗口里的标签页，直播画面作为「房间标签」嵌在内容区。

#### 布局

```
┌──────────────────────────────────────────────────────────────────────┐
│ ◉ LiveNotes    工作台  收听  资料            ⌘K      ● 3 路在听  ⚙  │ 40
├──────┬───────────────────────────────┬───────────────────────────────┤
│ 活动 │ 侧栏 236                       │ 标签栏                         │ 36
│ 栏   │ ┌───────────────────────────┐ │ [本场逐字稿 ×][收听 ×][阅读 ×] │
│ 48   │ │ 11-11 招商直播       ●    │ ├───────────────────────────────┤
│      │ │ 11-10 竞品复盘            │ │                               │
│ 🏠   │ │ + 新建 / 导入             │ │  当前标签内容                  │
│ 🎧   │ │                           │ │  · 工具页 = iframe             │
│ 🗂   │ │ 房间                       │ │  · 直播间 = 原生 WebView2      │
│ 👤   │ │ ● CH01 抖音    02:31      │ │                               │
│      │ │ ● CH02 快手    01:12      │ │                               │
│      │ └───────────────────────────┘ │                               │
├──────┴───────────────────────────────┴───────────────────────────────┤
│ 引擎正常 · 字幕延迟 0.8s · 已保存                              v0.1.0 │ 28
└──────────────────────────────────────────────────────────────────────┘
```

#### 信息架构

- **活动栏**：工作台 / 收听 / 资料（文件中心 + 人物）/ 设置。
- **侧栏**：当前模式的上下文列表——工作台下是场次，收听下是房间。
- **内容区**：标签页。工具页用 iframe 装现有页面；直播间标签用原生子视图。
- **状态栏**：引擎、路数、ASR 延迟、保存状态。

#### 核心交互

- **添加房间**：收听标签页顶部一个输入框，粘贴链接回车；不出现地址栏，不弹窗。
- **切房间**：点房间标签，或 `Ctrl+1..5`；其他房间的视图 `hide()`，采集不停。
- **关标签**：只关视图，房间继续在后台录；顶部「3 路在听」可重新打开。
- **进工作台**：点活动栏或标签；原本的收听标签保留，录音状态在标签圆点上继续闪。
- **登录**：房间标签内直接显示直播页；登录完成后继续留在标签里。

#### 技术落点

- 把 `browser.html` 的标签管理逻辑提升为**主窗口的标签管理**；`browser_enqueue` 不再打开第二窗口，而是把目标交给主窗口壳。
- 主窗口内容区用 iframe 承载 `/rooms`、`/reader` 等本地页；iframe 通过 `?embed=1` 隐藏页面自己的顶栏。
- 直播标签仍用 `room_open(window=main, x, y, w, h)`，位置由标签内容区的 `getBoundingClientRect()` 决定；切标签时 `room_show(false)`。
- 需要先验证主窗口（loopback 页面）能否调用 Tauri IPC，见第 7 节。

#### 优点

- 最接近现状，页面资产几乎全保留；
- 用户对「标签页」没有学习成本；
- 可以按标签逐个迁移，风险低；
- 第一阶段就能消灭「第二个窗口」。

#### 代价

- 仍然像「浏览器里套网站」，产品身份弱；
- 5 路 + 工具页会把标签栏挤爆，标题截断、状态难扫；
- iframe 带来焦点、滚动、快捷键、页面内 `window.open` 等一堆边角；
- 原生视图不能有圆角/阴影，标签内容区看起来会比较「硬」；
- 标签是「文档」心智，而直播间是「长时间运行的对象」，模型不完全贴合。

#### 工作量

约 **2.5–3.5 周**（1 名前端 + Rust 支援）：

| 工作 | 估时 |
|---|---|
| 主窗口壳 + 标签管理 | 5–7 天 |
| 现有页面 embed 模式（隐藏顶栏、事件） | 4–6 天 |
| 原生视图挂到主窗口 + 切换/隐藏 | 3–5 天 |
| 快捷键、空状态、回归 | 3 天 |

#### 什么时候选它

- 希望**最快**消灭弹窗，且短期不想动信息架构；
- 团队里只有 1 个人能改前端；
- 对「像 Claude Desktop」的要求主要是「单窗口」，不是「对象工作区」。

### 3.2 方案 B · 单窗口工作区（Workspace）——推荐

**一句话**：像 Claude Desktop / Linear 那样，左栏是「对象」，中间是「当前对象的主画布」，右栏是「这个对象的上下文」；没有标签页，切换靠选中对象。直播间是主画布，不是浏览器标签。

#### 布局（收听模式）

```
┌──────────────────────────────────────────────────────────────────────┐
│  ⌘K  搜索房间 / 场次 / 人物                        ● 3 路在听   ⚙  │ 36
├──────┬────────────────────┬──────────────────────────────────────────┤
│ 栏   │ 房间 3             │  CH01 · 抖音                    02:31    │ 56
│ 64   │ ┌────────────────┐ │  ● 在听   [静音] [字幕] [⋯]              │
│      │ │● CH01 抖音     │ ├────────────────────────────┬─────────────┤
│ 🏠   │ │  02:31  ▁▂▅▃   │ │                            │ 实时字幕     │

│ 🗂   │ │  01:12  ▂▃▂▁   │ │   （原生 WebView2）         │ 00:31 观众… │
```

#### 布局（工作台模式）

```

│ 栏   │ 场次 12            │  11-11 招商直播 · 02:31:20               │ 56
│ 64   │ ┌────────────────┐ ├────────────────────────────┬─────────────┤
│ 🏠   │ │ 今天            │ │  发言记录                   │ AI 总结      │
│ 🎧   │ │ ● 11-11 招商   │ │  [时间轴]                   │ 按内容/时间  │
│ 🗂   │ │ ● 11-11 竞品   │ │  [筛选 chips]               │ 分类/画像    │
│ 👤   │ │ 昨天            │ │  00:12 主播 …               │             │
│      │ │   11-10 …      │ │  00:18 观众 …               │ 要点可回溯   │

```

#### 信息架构

```
对象模型
  Room（直播间）──1:N──> Session（场次/录音）──1:N──> Utterance（发言）
     │                       │
     └ 平台/状态/健康度       └ 总结/高光/人物/分类

导航
  工作台  → 场次列表 → 逐字稿 + AI 总结
  收听    → 房间列表 → 直播舞台 + 实时字幕
  资料    → 文件中心 / 人物（两个子视图）
  设置    → 右侧面板（不跳页）
```

- **左活动栏 64px**：四个一级入口，常驻。
- **第二栏 260–300px**：当前模式的对象列表，可折叠；顶部固定搜索 + 添加。
- **主画布**：对象本身。
- **右栏 340–400px**：上下文，可折叠；收听下是实时字幕，工作台下是 AI 总结。
- **底部状态栏 28px**：引擎、路数、ASR 延迟、保存状态。

#### 核心交互

**开始收听**

1. 点「＋ 添加直播间」或 `Ctrl+L`，对象列表顶部展开一行输入框。
2. 粘贴链接回车 → 列表里立刻出现一张「解析中…」的房间卡（乐观 UI）。
3. Engine 建房间后卡片变「在听」，主画布自动选中这一路。
4. direct 失败时，卡片上直接出现「直取失败 · 切换浏览器采集」，点一下切换；页面只在需要时出现在画布上。

**日常监听**

- 对象列表每张卡有：平台、标题、时长、迷你电平/波形、状态点。
- 选中某一路 → 主画布显示画面（或信号画布），右栏显示这一路的实时字幕。
- `↑/↓` 切房间，`Ctrl+1..5` 直跳，`M` 静音，`Ctrl+K` 打开命令面板。
- 切到工作台，房间继续录；顶栏「3 路在听」始终在，点开可静音/停止/回到画面。

**登录 / 验证**

- 画布顶部出现提示条：「这一路需要登录才能采音 · [显示页面]」。
- 点开后原生页面占据画布，登录完点「完成并收起」，回到信号画布。
- 不新开窗口，不出现地址栏。

**异常**

- 房间卡变红，主画布显示诊断面板（原因 + 重试 + 切换采集 + 停止），不是一张死掉的网页。
- 状态栏和托盘同步异常计数。

**停止**

- 停止是显式动作，行内二次确认「停止后录音会收尾保存 / 取消」。
- 切走、关侧栏、切模式都不等于停止。

**关窗**

- 录制中关主窗口 → 拦截：「还有 3 路在录制」→「最小化到托盘 / 停止并退出 / 取消」。
- 这是录音类应用该有的默认行为，也和托盘的存在一致。

#### 原生视图的布局规则（关键）

因为 WebView2 子视图永远盖在 HTML 之上：

1. **只允许一个舞台矩形**：原生视图只出现在主画布的固定区域。
2. **浮层先隐藏**：命令面板、设置、确认框打开前 `room_show(false)`，关闭后恢复。
3. **面板用挤占**：右栏展开/收起时改变舞台宽度，不覆盖。
4. **不做圆角/阴影/裁剪**：用 1px 边框和周围留白制造「窗口」感。
5. **拖分隔条时先隐藏**：`pointerdown` 时 hide，`pointerup` 时按新尺寸 show，避免拖拽重影。
6. **切模式只 hide 不 close**：采集继续；只有「停止」才 close。
7. **快捷键走 Tauri 全局加速器**：焦点在原生页面里时，网页 JS 收不到键盘事件。

#### 技术落点

- 新壳放在 `app/web`（如 `/app` 或首页重构），桌面与网页共用；用 `window.__LN_DESKTOP__` 区分舞台实现。
- 主画布里放一个 `#stage` 占位元素；壳把它的 rect 报给 Rust，Rust 用 `room_open(window=main, ...)` / `room_layout` 定位。
- 房间选择、视图切换全部在壳内完成；`browser_enqueue` / 独立浏览器窗口退役，只保留托盘兜底一个版本。
- 工作台沿用现有 DOM 和三栏内容，只换外层壳和导航；筛选面板改成 HTML 浮层（工作台没有原生视图，浮层是安全的）。
- 直播页按需显示：默认显示「信号画布」（波形 + 状态 + 电平），需要登录/验证时才 `room_show(true)` 显示页面。

#### 优点

- 最像 Claude Desktop / Codex 的**对象工作区**，不是浏览器；
- 5 路房间在左栏一屏可扫，不需要标签栏；
- 录音状态终于成为全局状态；
- 工作台和收听共享同一个壳，视觉和交互统一；
- 「页面按需显示」让绝大多数时间只看到干净的产品 UI；
- 未来加监控墙、多屏、快捷键都顺。

#### 代价

- 信息架构改动最大，工作台需要重新排布；
- 现有页面要逐步从「整页」变成「视图」，不能一次性全改；
- 原生视图的焦点、缩放（Windows 125%/150%）、多屏 DPI 都要单独验证；
- 需要新增一层壳的路由/状态管理，前端复杂度上升；
- 第一阶段会和旧界面并存一段时间。

#### 工作量

约 **5–7 周**（1 名前端 + 1 名 Rust/全栈，可并行）：

| 工作 | 估时 |
|---|---|
| 设计 token + 壳骨架（活动栏/侧栏/主画布/状态栏） | 1 周 |
| 收听工作区：房间列表 + 舞台 + 实时字幕 + 全局录音状态 | 2 周 |
| 工作台：场次列表 + 逐字稿 + AI 总结 + 播放器重排 | 1.5 周 |
| 资料/设置/命令面板/快捷键 | 1 周 |
| 回归、DPI、焦点、异常路径 | 1 周 |

#### 什么时候选它

- 认可「房间是对象、录音是常驻状态」；
- 愿意用 5–7 周换一个真正像桌面产品的体验；
- 后面还要做 5 路监控、多屏、团队协作。

#### 可点击原型

静态原型（非生产代码）：[docs/prototypes/workspace-b.html](prototypes/workspace-b.html)；
包含收听、工作台、异常、页面模式、命令面板、添加房间等状态，截图在 `docs/prototypes/shots/`，
说明见 [docs/prototypes/README.md](prototypes/README.md)。

### 3.3 方案 C · 无页面控制台（Headless Console）

**一句话**：直播间网页只是采集管道，不是产品界面。App 是一个「监听控制台」：房间列表 + 大波形 + 实时字幕 + 关键词命中 + 告警；浏览器页面默认不可见，只在登录/排查时临时调出。

#### 布局

```
┌──────────────────────────────────────────────────────────────────────┐
│  LiveNotes 收听        ＋ 添加直播间          ⌘K        ● 4 路      │ 40
├──────┬───────────────────────┬───────────────────────────────────────┤
│ 栏   │ 房间                    │  CH01 · 抖音 · 02:31    ● 在听        │
│ 64   │ ● CH01 ███████ 02:31   │  ┌─────────────────────────────────┐  │
│      │ ● CH02 █████   01:12   │  │  实时字幕                        │  │
│ 🏠   │ ⚠ CH03 需登录           │  │  00:28 主播  …                   │  │
│ 🎧   │ ○ CH04 已停止           │  │  00:31 观众  …                   │  │
│ 🗂   │                        │  │                                  │  │
│ 👤   │                        │  └─────────────────────────────────┘  │
│      │                        │  波形 ▁▂▅▃▂  音量 -18dB  关键词 3      │
│      │                        │  [静音] [重试] [停止] [显示页面]       │
└──────┴───────────────────────┴───────────────────────────────────────┘
```

#### 核心差异

- **默认不加载直播页面**：抖音走 direct（ffmpeg 直取）；必须浏览器时，WebView2 以隐藏/离屏方式存在，用户看不见。
- **登录**：显式点「登录」，临时把页面调进画布，登录完收起。
- **画布是数据**：波形、电平、实时字幕、说话人、关键词命中、异常原因才是主视觉。
- **页面是调试工具**：`显示页面` 只给排查/确认用，不是主流程。

#### 技术落点

- 复用 direct 采集（`tools/direct_capture.py`，docs/13 已证明 5 路约 139MB / 3.1% CPU）。
- 浏览器兜底时，需要验证「隐藏的 WebView2 是否还持续出音频」；这是方案 C 的生死验证点。
- 如果不能隐藏，就退化为「离屏 1×1 窗口」或「保留画布但缩到角落」；再不行，C 不成立。
- 房间列表、字幕、状态全部来自现有 `/api/rooms`、`/api/live/*`，不需要改 Engine。

#### 优点

- 最干净、最「产品」的界面，完全没有浏览器味；
- 没有原生视图叠加问题，浮层、动效、圆角都能做；
- 内存最低（direct 5 路约 139MB，对比浏览器约 4.6GB）；
- 实时字幕和关键词命中可以做成真正的核心体验；
- 最适合「只听不看」的招商/招聘情报场景。

#### 代价

- 依赖 direct 覆盖：目前只有抖音；快手、B 站、需登录房间都要兜底；
- 隐藏 WebView2 的采集稳定性未验证，可能被节流/暂停；
- 登录、Cookie、反爬、平台改版风险都还在；
- 用户可能确实需要看画面（主播表情、贴片、屏幕文字、连麦）；
- direct 的合规风险 docs/13 已标注，需要产品/法务确认；
- 是四套方案里不确定性最高的。

#### 工作量

约 **6–9 周**，且必须先做 3–5 天 spike：

| 工作 | 估时 |
|---|---|
| Spike：隐藏/离屏 WebView2 采集稳定性 | 3–5 天 |
| 控制台壳 + 房间列表 + 字幕流 | 2–3 周 |
| direct 覆盖与兜底策略（平台矩阵） | 2 周 |
| 登录/验证/异常/诊断 | 1–2 周 |
| 回归与长稳 | 1 周 |

#### 什么时候选它

- 业务确认「监听时基本不需要看画面」；
- 愿意先投入 spike，接受 C 可能因隐藏采集不成立而回退；
- 把「5 路低内存长稳」当成第一优先级。

### 3.4 附：为什么不选 Electron

| 维度 | Tauri（现状） | Electron |
|---|---|---|
| 原生视图叠加 | WebView2 子窗口，盖在 HTML 上 | `<webview>`/`WebContentsView` 也有层级问题，但 `<webview>` 可以合成 |
| 5 路内存 | 浏览器视图约 3.5–4.6GB | 再叠一个 Chromium 壳，只会更高 |
| 本机余量 | 16GB，WSL 占 4GB，已多次 OOM | 更紧 |
| 迁移成本 | 0 | 重写壳、打包、更新、签名、托盘 |
| 决策记录 | docs/20 已接受 | 推翻 ADR |

结论：除非 `WebContentsView` 的合成能力是**唯一**能实现的设计前提，否则不值得。当前三套方案都不需要它。

## 5. 推荐路线：B 为目标，A 为第一步，C 为增强

不建议三选一后一次性重写。建议按下面的里程碑走，每个里程碑都能独立上线、独立回滚。

### M0 · 止血（2–3 天，可选）

- 把「收听」从 `window.open` 改成主窗口内跳转（`location.href='/rooms'`），收听页加「返回工作台」。
- 直播画面仍在独立窗口——只解决「点收听又弹一个窗口」的第一印象。
- 价值：演示/内测立刻不再尴尬；代价：临时方案，M2 会被替换。

### M1 · 单窗口壳（1.5–2 周） · ✅ 已交付

**交付**

- 主窗口由本地壳页 `desktop/dist/shell.html` 承担（`tauri.localhost`），现有引擎页先放进内容区 iframe；壳通过 Tauri IPC 管理原生子视图，通过 `postMessage` 接收 iframe 的操作请求。**不再把远程 `127.0.0.1` 页直接当主窗口**（见第 7 节 spike 结论）。
- 主窗口出现统一壳：活动栏 + 侧栏 + 主画布 + 状态栏。
- 收听页进入主画布；直播视图挂到主窗口的舞台区域；独立浏览器窗口退役（保留托盘兜底一个版本）。
- 全局「● N 路在听」状态与托盘、引擎健康打通。
- 页面顶栏统一隐藏，`?embed=1` 只保留内容。

**验收**

- 从主窗口点「收听」不再出现第二个窗口。
- 切到工作台，收听继续；切回来，画面和字幕还在。
- 5 路时列表可扫，状态不丢。

### M2 · 收听工作区（2 周） · ✅ 已交付第一版

**交付**

- 房间列表：状态分组、迷你波形、时长、异常原因、行内重试/切换/停止。
- 主画布：舞台 + 信号画布 + 「打开页面」；登录提示条。
- 右栏实时字幕：说话人、关键词命中、高价值标记。
- 添加房间：行内输入，支持分享文案抽链接。
- 快捷键：`Ctrl+K`、`Ctrl+L`、`↑/↓`、`Ctrl+1..5`、`M`。

**验收**

- 添加一路直播全程不出现地址栏、不出现新窗口。
- 直取失败 → 行内切换 → 继续录，路径不超过 2 次点击。
- 关主窗口时能拦截并说明还有几路在录。

### M3 · 工作台与资料（2–3 周） · ✅ 已交付第一版（嵌入模式）

**交付**

- 场次列表（按日期分组、搜索、收藏）。
- 逐字稿 + 时间轴 + 筛选 chips + 播放器，进入同一壳。
- AI 总结右栏；阅读/高光作为场次内的子视图，不再 `window.open`。
- 文件中心、人物并入「资料」。
- 设置改为右侧面板/命令面板入口。

**验收**

- 从收听点某一路的「回放」→ 工作台选中该场次，不整页刷新。
- 筛选、滚动、播放位置在切换后保留。
- 现有功能有对照清单，一项不缺。

### M4 · 增强（2 周，可与 M3 并行） · ✅ 已交付第一版

- 页面按需显示（信号画布为默认；登录才调页面）。
- 监控墙：2×2 / 3×2 房间卡（纯 HTML），点击聚焦。
- 命令面板补全：添加房间、搜场次、搜人物、停止全部、导出。
- 「在新窗口打开这一路」作为显式多屏功能（不是默认）。
- 浅色主题（可选）。

### 里程碑与方案的关系

```
M0 ── M1（A 的壳）── M2（B 的收听）── M3（B 的工作台）── M4（C 的按需页面）
```

- M1 用 A 的标签管理思路快速收口；
- M2 起把「标签」换成「对象列表 + 主画布」，就是 B；
- M4 把 C 的「默认无页面」接进 B 的舞台，不需要另起炉灶。

## 6. 横向设计决策（三套方案都适用）

### 6.1 对象模型

```
Room（直播间）
  id / platform / title / status / health / startedAt / waveform
    │ 1:N
Session（场次/录音）
  id / startedAt / duration / speakers / transcript / summary / highlights
    │ 1:N
Utterance（发言）
  t / speaker / text / categories / value
```

- **Room 是「正在发生」，Session 是「已经留下」**。
- 收听按 Room 组织，工作台按 Session 组织，人物跨两者。
- 这个模型决定了：房间不能做成「标签页」（标签是文档心智），应该做成列表里的长寿命对象。

### 6.2 窗口与多屏

- 默认**单窗口**。
- 「在新窗口打开这一路」是显式的专家动作，放在 `⋯` 菜单里，不放在主流程。
- 未来「监控墙窗口」可作为第二窗口，专门给第二块屏；仍然不是默认。
- 录制中关主窗口必须拦截：最小化到托盘 / 停止并退出 / 取消。

### 6.3 原生视图规则（WebView2）

| 规则 | 原因 |
|---|---|
| 只允许一个舞台矩形 | 子视图是原生窗口，无法被 HTML 裁剪 |
| 浮层打开前 hide，关闭后 show | 否则命令面板会被页面盖住 |
| 右栏/侧栏用挤占，不覆盖 | 避免「面板被直播页挡住」 |
| 不做圆角/阴影 | 原生视图不支持，统一用 1px 边框 |
| 拖分隔条时先 hide，松手再 show | 避免拖动时黑边/重影 |
| 切视图 hide，不 close | 采集要继续 |
| 快捷键用全局加速器 | 焦点在原生页面里时网页收不到键盘 |

### 6.4 导航、键盘、命令面板

- **活动栏**是一级导航；**对象列表**是二级；**主画布**不承担导航。
- `Ctrl+K`：命令面板（添加房间、搜场次、搜人物、停止全部、导出、设置）。
- `Ctrl+L`：添加直播间（相当于浏览器的地址栏，但只在收听模式有效）。
- `↑/↓`：在对象列表移动；`Enter`：打开；`Ctrl+1..5`：跳到第 N 路。
- `M`：静音当前房间；`Space`：工作台播放/暂停；`Esc`：关闭面板/取消输入。
- `Alt+←/→`：对象历史，不是页面历史。
- 所有快捷键在原生页面获得焦点时也要生效——用 Tauri 全局快捷键，不依赖网页 keydown。

### 6.5 状态与反馈

| 状态 | 呈现 |
|---|---|
| 引擎健康 | 状态栏左侧常驻；异常时红色 + 托盘同步 |
| 正在录 N 路 | 顶栏右侧常驻胶囊；点开房间快捷操作 |
| ASR 延迟 | 状态栏，>3s 变琥珀 |
| 保存状态 | 状态栏「已保存 / 保存中」 |
| 房间异常 | 列表卡片红色 + 主画布诊断面板，不用 toast |
| 操作成功 | 轻量 toast，2.6s 自动消失 |
| 需要决策 | 行内确认/浮层，不用系统模态 |

原则：**能用状态栏表达的，不用 toast；能用行内表达的，不用弹窗。**

### 6.6 视觉语言

以收听页现有的深色信号语言为基底，统一到整个 App：

| Token | 建议值 | 用途 |
|---|---|---|
| `--bg` | `#0A0C0F` | 窗口底 |
| `--surface` | `#12161B` | 面板/卡片 |
| `--surface-2` | `#171C22` | 悬浮/选中 |
| `--line` | `#232A33` | 1px 分隔 |
| `--ink` | `#E8E6E1` | 主文字 |
| `--muted` | `#98A2AE` | 次要 |
| `--accent` | `#E6B566` | 唯一强调色（琥珀） |
| `--ok` | `#7FD1AE` | 在听/健康 |
| `--bad` | `#E8776D` | 异常/停止 |
| `--info` | `#8FB4D9` | 中性提示 |

- 中文正文 13px / 1.6；时间、ID、数值用等宽 + tabular numerals。
- 控件高度 28/32/36；间距 4/8/12；圆角 8/10。
- 动效 120–180ms ease；面板滑动可以动，原生视图的尺寸变化不要动。
- 边框优先于阴影；一个强调色，不要蓝+琥珀+绿同时抢。
- 波形是品牌元素：列表缩略、画布主视觉、状态栏都可以复用。

### 6.7 文案

| 现在 | 改成 | 原因 |
|---|---|---|
| 应用内浏览器 | 直播画面 / 网页 | 「浏览器」是实现词，不是用户词 |
| 关掉这个页面不影响录音 | （删掉）状态栏显示「采集在后台运行」 | 不需要解释设计债 |
| 多房间采集 Spike | 收听 | 内部代号不能出现在产品里 |
| 停止并关闭 | 停止收听 | 用户关心的是「停止」，不是「关闭标签」 |
| 开始听 | 开始收听 | 和导航一致 |

## 7. 技术验证清单（M1 前必须做）

> **2026-11-11 spike 结果**：第 1 条已出结论——路线 a 仅加 `remote.urls` 不够，Tauri 2.12.5 对远程 origin 的自定义命令还要求 app ACL manifest；M1 改走路线 b（本地壳 + iframe）。第 2、3 条在 100% 缩放下通过。详见 [docs/24 · M1 Spike 报告](24-m1-spike-report.md)。

1. **主窗口 IPC**：主窗口加载的是 `http://127.0.0.1:<port>`，Tauri 默认不给远程页面 IPC。三条路选一条：
   - a. 在 capability 里给 loopback 加 `remote.urls`（最快，需安全评估）；
   - b. 主窗口改成本地 `desktop/dist/shell.html`，iframe 引擎页（最安全，但桌面独有，需 CORS/消息桥）；
   - c. 复用现有 `rooms::start_room_watcher`：页面 → Engine → Rust 控制通道（最解耦，但需要新增 stage/selection 接口）。
   **建议先试 a，1 天内出结论；不行走 b。**
   **实测**：a 的简单版失败（`spike_report not allowed. Plugin not found`）；b 通过（本地页 `room_open/room_show/spike_report` 均成功）。**采用 b。**
2. **子视图挂主窗口**：`window.add_child` 在 main window 上定位、resize、hide/show、focus 的行为；DPI 125%/150% 下的逻辑坐标。
3. **z-order**：命令面板/设置/确认框出现前 hide 原生视图，关闭后恢复；确认无闪烁、无焦点丢失。
4. **后台采集**：切走/隐藏的房间视图是否继续出块；5 路并发 10 分钟长稳。
5. **iframes（方案 A）**：现有页面在 iframe 里的滚动、快捷键、`window.open`、localStorage 是否正常；是否需要 `?embed=1`。
6. **全局快捷键**：焦点在原生直播页里时，`Ctrl+K`、`Ctrl+1..5` 仍生效。
7. **隐藏采集（仅方案 C）**：隐藏/离屏 WebView2 是否持续出音频；不行则 C 不成立。
8. **内存**：5 路浏览器视图 + 壳的提交内存；本机 16GB + WSL 4GB 的余量。

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 页面视图化回归 | 现有功能丢失 | 功能对照清单；M3 前旧页面保留 `?legacy=1` |
| 原生视图焦点/DPI | 键鼠体验异常 | M1 spike；125%/150%/双屏各验一遍 |
| 两套 UI 并存 | 用户困惑 | 一个版本内只用一套；旧窗口只留托盘兜底 |
| 用户肌肉记忆 | 「收听」找不到 | 活动栏保留同名入口；首次切换做一次引导 |
| 5 路内存 | 卡顿/OOM | direct 优先；监控墙用纯 HTML 卡片；必要时限制浏览器路数 |
| iframe 边角 | 方案 A 的隐藏成本 | 只把 iframe 当过渡；M2 起逐步视图化 |
| 主窗口 IPC 安全 | 本地页面拿到壳能力 | 优先本地 shell；loopback capability 只放行必要命令 |

---

## 9. 决策记录（2026-11-11）

1. **目标形态**：采用 **方案 B（单窗口工作区）**；M1 先用方案 A 的壳收口，M2 起换成对象列表 + 主画布。
2. **画面依赖**：默认看信号画布；直播页面按需显示（M4），登录 / 排查时再调出。
3. **关窗行为**：录制中关主窗口默认最小化到托盘；`LIVENOTES_CLOSE_TO_TRAY=0` 可关闭拦截（调试用）。
4. **多屏**：第一版不做第二窗口；后续如需多屏，再加显式「在新窗口打开这一路」。
5. **主题**：壳与收听用深色信号语言；工作台 / 资料 / 设置暂时保留浅色旧页面，套深色画框。
6. **网页版**：桌面端先单窗口，网页版保留旧的多标签行为，后续再共享壳。

## 10. 一页纸总结

- **问题**：不是窗口位置，是页面模型 + 浏览器模型 + 录音模型叠在一起。
- **目标**：一个窗口、一个对象列表、一个主画布；录音常驻可见。
- **A**：单窗口标签式，2.5–3.5 周，最快止血，仍像浏览器。
- **B**：单窗口工作区，5–7 周，最像 Claude Desktop，推荐为目标。
- **C**：无页面控制台，6–9 周 + spike，最干净也最不确定。
- **路线**：M0 止血 → M1 单窗口壳 → M2 收听工作区 → M3 工作台 → M4 页面按需/监控墙。
- **先验证**：主窗口 IPC、子视图挂载、z-order、后台采集、全局快捷键。
