# 实时链路并发改造：共享 ASR 工作池

## 背景

改造前，每个 `LiveSession` 有一条采集线程，线程里直接调用 `ENGINE.transcribe()`；
`Engine.transcribe()` 用一把进程级 `_decode_lock` 包住整个解码过程。后果：

- 10 路同时有人说话时，所有解码严格串行；一路的长句会阻塞所有路的字幕；
- 滚动字幕每秒解码一次，和更重要的定稿抢同一把锁；
- 会话数一多，线程都在等锁，CPU 用不满，延迟却随路数线性增长；
- 单会话的 PCM 队列只丢最旧的块，没有跨会话的公平调度或优先级。

这不是换更快的模型能解决的：模型再快，队头阻塞和跨会话不公平仍在。

## 改造后的结构

```
每路采集线程（VAD/断句） --submit--> AsrPool 调度器 --dispatch--> N 个 ASR worker
```

代码位置：

| 文件 | 作用 |
|---|---|
| `app/asr_pool.py` | 工作池、跨会话轮转、优先级、合并/TTL、有界队列、延迟统计 |
| `app/live.py` | `Engine.transcribe()` 去掉全局锁；采集线程只做 VAD/入队；定稿回调 `commit_final()`、临时字幕回调 `apply_partial()` |
| `app/config.py` | 线程数、队列上限、TTL 等配置 |
| `tools/selftest_asr_pool.py` | 调度器的确定性自测（不需要模型） |
| `tools/stress_live.py` | 1/3/5/10 路实时压测，输出 RTF/延迟/丢块/CPU/内存 |

### 调度规则

1. **识别器单例共享**：sherpa-onnx 官方说明 `OfflineRecognizer` 线程安全、
   `OfflineStream` 不能跨线程共享；CPU provider 下多个线程各自 `create_stream()`
   后并发 decode 即可。因此不复制 240MB 的 SenseVoice 模型，只在每个 worker
   里放一个 28MB 的 CAM++ 声纹提取器，避免 embed 成为新的全局串行点。
2. **定稿优先**：会话内先派定稿；只有没有定稿排队、也没有定稿在跑时，才派临时字幕。
3. **同会话定稿串行**：声纹在线聚类和落库依赖句子顺序，所以一个会话同一时刻
   只允许一条定稿在跑，其余按提交顺序排队；不同会话之间并行。
4. **临时字幕合并 + TTL**：每会话最多一条在跑 + 一条待跑，新帧覆盖旧帧；
   切句/暂停会递增「代」，迟到的旧结果直接丢弃；排队超过
   `LIVENOTES_PARTIAL_TTL_S`（默认 2.5s）直接过期。
5. **跨会话轮转**：每次派活后游标前进，避免某一路持续说话饿死其他路。
6. **有界队列**：单会话定稿积压超过 `LIVENOTES_ASR_MAX_PENDING_FINALS`（默认 8）
   时丢最旧的一条并计数；最终体现在场次的「未转写」时长里。
7. **收尾排空**：`LiveSession.stop()` 先等采集线程退出，再 `drain_session()` 等所有
   排队定稿跑完，最后才重聚类/更新场次摘要，不会丢最后几句。

### 可观测字段

- `GET /api/live/status?id=...` 的 `asr`：该会话的排队数、丢句数、RTF、
  定稿/临时字幕 P50/P95、排队等待。
- `GET /api/live/info` 的 `asr`：全局工作池状态（worker 数、忙碌数、总丢句、
  总 RTF、全局延迟窗口）。
- 压测脚本读同一份统计，所以线上看到的数和压测报告口径一致。

## 指标口径

- **RTF** = ASR 解码耗时 / 送进解码器的音频秒数（定稿 + 临时字幕）。
- **定稿 P50/P95**：这句话最后一个采样到达服务端 → 定稿落库上屏的墙钟时间。
  包含 VAD 等静音/等 4 秒强切、排队、解码、声纹、写库；不是只算 decode。
- **临时字幕 P95**：临时字幕音频到达 → 上屏（排队 + 解码）。
- **定稿丢句率** = 被工作池丢掉的定稿 / 提交的定稿。
- **PCM 丢块率** = 浏览器 256ms 块进入会话队列时被丢的块 / 总块数。
- **CPU** = 进程内所有线程的 `process_time` 增量 / 墙钟（占用的核数）。
- **RSS** = 进程 Working Set 峰值。

## 实测

环境：Windows 10、12 核、Python 3.13、sherpa-onnx 2.0.1、SenseVoiceSmall-int8 + CAM++。
配置：8 个 ASR worker，单次解码 4 个 ONNX Runtime intra-op 线程。音频取仓库里
1451 秒的 16k 单声道录音，各路线从不同位置循环播放，实时推流。

### 10 路 × 10 分钟长稳

配置同上（8 worker / 4 线程），预热 30 秒不计，稳定态测量 600 秒：

| 指标 | 结果 |
|---|---|
| 定稿句数 | 1640 |
| RTF | 0.078（解码 1013s / 送入解码器 12991s 音频） |
| 定稿 P50 / P95 | 0.342s / 0.903s |
| 临时字幕 P95 | 0.236s |
| 定稿排队 P95 | 0.000s |
| 定稿丢句率 | 0.00%（0 / 1640） |
| PCM 丢块率 | 0.00%（0 / 23431 块，约 5998s 音频） |
| 识别错误 / 推流错误 | 0 / 0 |
| CPU 均 / 峰 | 4.3 / 5.9 核 |
| RSS | 1105MB → 1166MB（峰值） |

稳定性：

- 每秒采样的 `pending_finals` 全程为 0，10 路同时说话时解码能力仍有富余，
  不存在排队堆积；
- RTF 首分钟 0.083、末分钟 0.078；定稿 P95 首分钟 0.962s、末分钟 0.917s，
  延迟不随运行时间恶化；
- RSS 从 1105MB 涨到 1166MB（+61MB），其中前 2 分钟约 +31MB，之后约
  +5MB/分钟且继续放缓；同期没有队列或延迟增长；
- 2 小时级别的内存漂移仍需正式长稳确认，见下方「复现」中的 2 小时命令与
  「已知现象与边界」。

1 路 × 10 分钟同口径基线（同样预热 30 秒、测量 600 秒）：

| 指标 | 1 路 | 10 路 | 10 路 / 1 路 |
|---|---:|---:|---:|
| RTF | 0.047 | 0.078 | 1.66x |
| 定稿 P50 | 0.243s | 0.342s | 1.41x |
| **定稿 P95** | **0.844s** | **0.903s** | **1.07x（验收 ≤ 2x）** |
| 临时字幕 P95 | 0.147s | 0.236s | 1.61x |
| 定稿丢句率 | 0.00%（0/160） | 0.00%（0/1640） | - |
| CPU 均 / 峰 | 0.5 / 1.4 核 | 4.3 / 5.9 核 | - |
| RSS 峰 | 1028MB（起 872MB） | 1166MB（起 1105MB） | - |

1 路只有 160 句定稿，RSS 却上涨约 156MB，且同样集中在前 2 分钟；说明这段
增长主要来自模型/运行时工作集与分配器的预热，而不是随定稿条数线性累积。
这不替代 2 小时长稳，只是解释 10 分钟曲线的形状。

## 复现

```bash
# 调度器确定性自测（不需要模型/音频）
python tools/selftest_asr_pool.py

# 1/3/5/10 路 × 60 秒
python tools/stress_live.py --tracks 1,3,5,10 --duration 60 \
    --json data/asr-stress-60s.json --md data/asr-stress-60s.md

# 正式 2 小时长稳（4 档共约 8 小时）
python tools/stress_live.py --tracks 1,3,5,10 --duration 7200 --warmup 60 \
    --json data/asr-soak-2h.json --md data/asr-soak-2h.md
```

压测默认把数据库/录音写到临时目录，不污染真实场次；结束时自动删除，`--keep-data` 可保留。
JSON 里的 `levels[*].samples` 是每秒采样的 CPU、RSS、RTF、排队数曲线。

## 已知现象与边界

- 多路压测时 sherpa-onnx 的原生 VAD 会打印
  `circular-buffer.cc ... Invalid n: -xxxx`：这是 silero VAD 对「短于人声静音阈值」
  的瞬时语音片段的已知行为（返回空段，不落库）。本次改造没有改 VAD 参数，
  该现象在改造前同样存在；压测中定稿条数与单路一致，没有因此丢句。
- 共享识别器的线程安全保证针对 **CPU provider**；本项目固定 `provider="cpu"`，
  没有使用 CUDA。
- 2 小时长稳需要在目标机器上按上面的命令运行；本报告中的 60 秒（1/3/5/10 路）
  和 10 分钟（1/10 路）结果都是稳定态采样，不能替代 2 小时内存/积压漂移的验收。
