# 11 · 前端改造方案（单体单文件 → 可维护）

> 结论先行：**先抽共享层 + 页内分层（方案 B，2–3 人天），再按需拆文件（方案 A，加 2 人天）**。
> 两者是同一条路的两个阶段，B 做的分层在 A 里原样保留、不返工。
> **方案 C（Vite + 组件框架）不建议现在做**：它唯一不可替代的收益是"组件化 + 单测"，
> 代价是给一个纯 Python、纯本地、零依赖的仓库引入 Node 工具链和离线安装风险。

| 移动端 | `index.html` 一个 `@media (max-width:1024px)` 块（约 95 行 CSS）+ `bindUI` 尾部约 150 行 Tab 逻辑 | 决策已定：同文件响应式，不做 `/m` 副本（docs/06） |

## 2. 把痛点翻译成工程问题

| 你的感受 | 实际是什么 | 量级 |
| --- | --- | --- |
| "改一个交互要在大文件里找上下文" | 2,094 行 JS 里 122 个同级函数，靠全文搜索跳转；状态 `S` 被 40+ 个函数读写 | 定位成本 = 每次改动 3–5 次跳转 |
| 同上 | CSS / HTML / JS 三段按"页面"切，没按"功能"切；`refresh()` 调用链横穿筛选、列表、时间轴、总结四条线 | 牵一发动全身 |
| "移动端只做了适配决策" | 移动端行为（Tab 切换、更多面板、面板显隐）混在 `bindUI` 与 `apply()` 里，和桌面逻辑纠缠 | 每加一个移动端交互都要读整段 |
| 没提到的隐性成本 | 10 份拷贝的 helper 已经漂移，同一个 `api()` 在不同页面行为不同 | 修 bug 要改 10 处，且容易只改 7 处 |

**真正要解决的三件事**：① 一处改动只碰一个文件 / 一段代码；② 共享概念只有一份实现；③ 重构本身可验证（现在没有）。

## 3. 不能违反的约束

1. **零外部依赖、纯本地**：`README` 与 `docs/06` 都把它当卖点；不能引入 CDN，也不能假设部署机能联网装 npm 包。
2. **无构建**：`python run.py` 起来就能用；改一行前端刷新即生效。任何方案都要保住这条（或至少保住"不构建也能跑"）。
3. **服务端不动**：`/static/` 现成，拆文件纯前端行为。
4. **移动端单份代码**：docs/06 已否决 `/m` 副本（双份同步维护），不要回头走这条路。
5. **8 个小页面（143–586 行）不改结构**：它们的问题只是"抄了一份 helper"，换引用即可。

## 4. 三个方案

### 方案 A · 拆文件，不换技术栈（原生 ES Module）

**目标形态**：`index.html` 从 3,116 行降到 ~320 行，只剩结构与资源引用；CSS 按"令牌 / 基础 / 移动端 / 页面"四层；JS 按业务域切成 11 个模块，最大 ~450 行。
仍使用原生 JS 与 `querySelector`，不引入框架、不引入打包器 —— 浏览器直接加载 ESM，服务端 `mimetypes` 已能正确返回 `text/javascript`。

```
app/web/
  index.html              ~320 行（结构 + <link> + <script type="module">）
  rooms.html              ~110 行
  css/
    tokens.css            ~60    设计令牌（现在 9 份拷贝）
    base.css              ~120   顶栏 / 按钮 / 弹层 / toast 等跨页复用
    mobile.css            ~180   断点规则，从 index 的 @media 搬出
    index.css             ~430   仅 index 独有
    rooms.css             ~430
  js/
    shared/  dom.js  http.js  format.js  ui.js        （~200 行，替代 10 份拷贝）
    index/   state.js session.js filters.js list.js summary.js
             classify.js live.js player.js settings.js search.js
             mobile.js main.js                        （每模块 80–450 行）
    rooms/   state.js render.js actions.js canvas.js poll.js main.js
```

**迁移步骤**（每步独立可合并、可回滚）：

1. **抽共享层**（不改行为）：新建 `shared/*.js` + `tokens.css` / `base.css`，10 个页面全部改为引用，删掉各自副本。验收：每页功能不变。
2. **拆 CSS**：`index.html` 的 695 行 CSS 按四层切开；`rooms.html` 同样。
3. **拆 JS**：`<script type="module">`，模块间 `import`；`main.js` 负责串联 `init()`。
4. **统一 rooms**：rooms 已经是 IIFE 骨架，改成模块几乎是机械替换。
5. **收尾**：`/static/` 加 `Cache-Control: no-cache`；删死代码；更新 README 与 docs。

**已知坑（都已核实）**：

- 内联 `onclick=` 为 0 → 转模块不会丢绑定。
- `type="module"` 是 defer 语义：现有"脚本末尾直接调 `init()`"的写法仍然成立，但要确认没有依赖 `window.onload` 的时序。
- 模块要求 `http://` 打开（`file://` 会 CORS 失败）。当前页面本来就靠 `fetch` 跑 API，`file://` 一直不可用 → **不是回归**。
- 全局变量消失后，控制台直接调 `renderLive()` 的调试习惯会失效 → 开发期在 `main.js` 暴露 `window.__app`。
- 服务器不设缓存头：不加 `no-cache`，改了 JS 刷新看不到效果，会浪费半天排查。

**工作量**：3–5 人天。**风险**：低。

---

### 方案 B · 不拆文件，只拆结构（约定式分层）

**目标形态**：`index.html` 仍是单文件，但按 `rooms.html` 已验证的骨架重排成六段：
`配置 / 状态 / 派生 / 渲染 / 动作 / 网络轮询`，每段一条 banner 注释；27 个顶层可变全局收敛进一个 `state` 对象；所有写 DOM 的语句集中到"渲染"段。
同时抽出共享层（同 A 的第 1 步，这是唯一"拆"的部分）。

**具体动作**：

1. 共享层抽取（同 A 第 1 步）。
2. 按功能给 `index.html` 的 JS 重新排序分段，`S` → `state`，补上派生函数（现在 `activeFilters`、`qs` 这类散落在中间）。
3. 把 `bindUI` 拆成"桌面"与"移动端外壳"两个函数，移动端逻辑独立成段。
4. 移动端 CSS 里的 `@media` 块本来已是连续的 ~95 行，只需加 banner 与目录注释。

**工作量**：2–3 人天。**风险**：很低（不改运行模型、不加加载方式）。
**代价**：文件仍有 2,000+ 行；跨页共享解决不了（只解决 helper 级），页面级组件（如场次切换器）仍然抄两份。

---

### 方案 C · 引入构建 + 组件框架（Vite + Preact / lit）

**目标形态**：真正的组件化与状态管理，可写单元测试。
选型建议：**Vite + Preact（~3KB）+ htm**（无需 JSX 编译）或 **lit-html**；不建议 Vue/React 全家桶。

**必须接受的改动**：

- 仓库从"纯 Python"变成"Python + Node"：`package.json`、`npm ci`、CI 增加 build 与测试步骤。
- 构建产物 `app/web/dist/`，`server.py` 的 10 条路由要改指向 dist（或构建直接覆盖源文件，风险更高）。
- 开发流程改造：`vite dev` + 代理 `/api → 127.0.0.1:8765`，`run.py --reload` 保持不动。
- **最大风险：离线/内网安装 `node_modules`**。如果目标部署机不能联网，需要私有 registry 或把依赖 vendored 进仓库 —— 这与"纯本地、可拷贝即用"的定位直接冲突。

**收益**：组件复用、单测（vitest）、可选 TS、状态集中。
**工作量**：10–15 人天（index + rooms + reader 三个复杂页）。**风险**：高。

## 6. 推荐路线

**第 0 期（半天，无论选哪个方案都先做）：给重构装上刹车。**
现在没有任何前端自动化验证，动 3,000 行文件等于蒙眼改。加一个 ~40 行的冒烟脚本：
用 headless Chrome 逐个打开 10 个页面（`--virtual-time-budget` + `--dump-dom`），断言
① 页面返回 200；② 关键选择器存在（如 `#sessTitle`、`#tbl`、`.m-tabbar`）；③ 控制台无报错。
放进 CI 的 pytest 里跑。它恰好能抓住拆分后最典型的故障 —— 模块 404 或语法错导致整页白屏。

**第 1 期（2–3 人天）：方案 B。** 抽共享层 + index 内部分层。这一步解决 60% 的定位成本，且不改变任何运行方式。

**第 2 期（+2 人天）：方案 A 剩下的部分。** 把已经分好段的 JS 按段拆成文件，CSS 按层拆。因为第 1 期已经把边界划清，这一期是机械操作。

**方案 C 的触发条件**（满足再立项，不要先做）：
- 前端页面数还要翻倍，或出现 3 个以上"同一种卡片/列表"在不同页面重复实现；
- 团队里有人长期维护前端，且能解决 node_modules 的离线分发；
- 需要单测覆盖复杂交互（如实时字幕的状态机）。

## 7. 明确不做的事

- **不给 8 个小页面做结构改造**：它们每个 143–586 行，改结构收益低于风险，只换共享引用。
- **不做 `/m` 移动端副本**：docs/06 已论证双份维护成本，继续走同文件响应式。
- **不引入打包器只为"看起来现代"**：本项目零依赖、单进程、可拷贝即用，这是它的优势，不是缺陷。
- **不在没有冒烟脚本的情况下动 `index.html`**：3,116 行、122 个函数、0 测试，先有网再动刀。

## 与原方案的三处偏差

1. **没有做全局 `tokens.css`。** 实测 10 个页面里逐字节相同的 CSS 规则只有 36 条，
   而且 `index.html`（浅色）与 `rooms.html`（深色）是两套完全不同的设计语言。
   强行抽一份公共令牌，要么改变现有颜色，要么只是把同样的内容换个位置。
   结论：样式按页成文件，不做全局令牌层。
2. **没有跨页统一 JS helper。** `api()` 在 glossary / highlights / pushes / reader 里
   HTTP 非 2xx 时抛错，在 library / people 里不抛；`fmt()` 有 4 种输出（是否补小时位、
   是否四舍五入）。统一它们会改变页面显示与错误路径，那是行为变更，不该混进结构重构。
3. **B 与 A 合并为一次。** 见上。

## 怎么验证的

- **像素级比对**：改动前后各截一张图（1440×900 与 390×844 两种宽度），
  `cmp` 字节一致才继续。index 与 rooms 在两个宽度下都完全一致。
- **浏览器冒烟**：`tools/ui_smoke.py` 逐页打开，断言关键节点存在、控制台无
  `Uncaught` / 语法错。10/10 通过；先做过一次负向验证（故意 `throw`），确认它能报错。
- **ESM 静态检查**：所有模块过 `node --check`；另用脚本扫过"给导入绑定赋值"这类
  只在运行时会炸的错误（实际抓到 `_gqTimer` 一处，已把它归到 `main`）。
- **后端回归**：`python -m pytest` 200 项全过。
