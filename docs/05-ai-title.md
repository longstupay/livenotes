# 场次标题：并进 AI 总结的「顺手起名」设计

> 版本 v0.2 · 面向 LiveNotes v0.1 现有实现（`app/reader.py` / `app/analysis.py` / `app/live.py` / `app/web/index.html`）
> 一句话：**标题是「读懂了这场直播」的副产品，不是独立的创作任务。**

---

## 1. 现状：三处各起各的名，每次都重新烧一遍 token

| 触发点 | 现在的调用 | 问题 |
| --- | --- | --- |
| 结束保存 `live._auto_finalize` | 先 `reader.suggest_title()`（1 次 LLM，抽 40 句）→ 再 `analysis.make_summary()`（1 次 LLM，最多 800 句，长直播按时间分层抽样） | 同一份内容读两遍；起名那次只看到 40 句抽样，没有全局视角 |
| 点 ✎ 改名 `index.renameSession` | 再调一次 `/api/sessions/suggest_title`（第 3 次 LLM） | 候选和刚才生成的一模一样，纯浪费 |
| 阅读页改名 `reader.html` `doRename` | 又调一次 `suggest_title` | 同一个功能，第 4 份实现 |

截图里的四个候选，就是这条链路的直接产物：

- `普通人做大棚蔬菜怎么找销路 · 03:41` —— LLM 被限制「≤12 汉字、不要标点」，为了压缩牺牲可读性，出来像口令
- `看你在线能不能卖出去 · 03:41` —— ASR 原句直接当标题，没有主语、没有上下文
- `你们那个你们就这方面我太不… · 03:41` —— 半句话 + 错字，**这是最伤的一档**
- `5 人连麦 · 03:41` —— 结构信息，不是名字

三个具体病灶：

1. **`stamp()` 硬加 ` · HH:MM`**（≤18 字就加）。时间在列表副行、播放器、导出文件名里都已经有了，写在名字里只会让它更像文件名而不像名字。
2. **候选没有"来源"区分**，用户分不清哪句是 AI 想的、哪句是机器听错的。
3. **起名的上下文比总结窄一个量级**：总结知道有几个话题、谁在讲什么、结论是什么；起名只看到 40 句碎片。

---

## 2. 设计原则

1. **一次调用，两件事**：summary 的 JSON 里直接多一个 `title` 和两个 `title_alts`，输出增量约 40–60 token，输入零增量。
2. **一次生成，处处复用**：改名弹层、列表、导出、阅读页全部读同一份缓存，不再二次请求。
3. **建议与决定分离**：AI 只负责"给候选"，是否覆盖由「这个名字是谁起的」状态机决定。
4. **宁可不出名，也不出噪音**：任何一级候选不合格（空、纯标点、半句、超长）就降级，最差保留默认名。

### 备选方案对比

| 方案 | token | 质量 | 结论 |
| --- | --- | --- | --- |
| A 并进总结调用（本文） | 1 次，+40 token 输出 | 高（全局视角） | ✅ 推荐 |
| B 截 overview 首句当标题 | 1 次，0 增量 | 低（120 字概述截断必成病句） | ❌ |
| C 保持独立起名调用 | 2–3 次 | 低（只见 40 句） | ❌ 现状 |
| D 等用户点改名才生成 | 1 次（触发晚） | 高 | ⚠️ 首次打开要等，且列表长期是「抖音直播 2026/11/5…」 |

## 3. 方案 A：总结调用里顺带出标题

### 3.1 输出协议（两个 prompt 都要改）

```json
{
  "title": "大棚菜销路：连麦里问最多的三个坑",
  "title_alts": ["五个人聊大棚：谁在赚谁在亏", "从种到卖，卡在哪一步"],
  "overview": "……",
  "points": [ …… ]
}
```

写进 prompt 的硬规则（照抄，别让模型自由发挥）：

- 长度 **6–16 个汉字**（中英混排按字符算，整体 ≤ 24 字符）
- **名词短语或判断句**；禁止疑问句、禁止「怎么 / 如何 / 能不能」开头
- 必须能区分场次：**对象 × 主题 × 场景**，不要只写主题
- 禁用空词开头：本期 / 这期 / 今天 / 这场 / 直播 / 分享 / 干货 / 复盘 / 连麦
- **不要写日期、时间、人数**（系统已有，写了就重复）
- 不加引号、书名号、句末标点，不加 emoji，不换行
- 三个候选**角度必须不同**：① 主题+对象 ② 结论/观点 ③ 场景+冲突
- 内容不足以起名（有效发言 < 15 条，或全是闲聊广告）→ `title` 返回 `null`

对照片子里的效果：

| | 现在的候选 | 改后 |
| --- | --- | --- |
| 主 | `普通人做大棚蔬菜怎么找销路 · 03:41` | `大棚菜销路：连麦里问最多的三个坑` |
| 备 1 | `看你在线能不能卖出去 · 03:41` | `五个人聊大棚：谁在赚谁在亏` |
| 备 2 | `你们那个你们就这方面我太不… · 03:41` | `从种到卖，卡在哪一步` |
| 备 3 | `5 人连麦 · 03:41` | 只在无 LLM / 内容太短时出现，且降级为弱样式 |

### 3.2 数据模型

`sessions` 加三列（`_migrate` 迁移，不动历史数据）：

| 列 | 取值 | 用途 |
| --- | --- | --- |
| `title_source` | `default` / `auto` / `auto_local` / `user` / `legacy` | 决定"能不能自动改"、UI 是否显示「AI 命名」徽标 |
| `title_alts_json` | JSON 数组 | 改名弹层零请求直接读 |
| `title_updated_at` | ISO 时间 | 排查"这名字什么时候变的" |

老库推断：标题匹配默认前缀（`抖音直播` / `直播监听` / `标签页直播`）→ `default`，其余 → `legacy`（**视为用户命名，永不自动覆盖**）。

为什么不全塞 `summaries.payload`：标题是场次的属性，列表、搜索、导出、文件名都要用，必须有列。payload 里仍然保留一份，用于回答"这名字是哪次总结起的"。

### 3.3 写回状态机（核心，别写成一坨 if）

| 当前 `title_source` | 本次总结情况 | 行为 |
| --- | --- | --- |
| `default` | LLM 成功且 title 合法 | 写主标题，`title_source=auto`，飘一条「已按内容命名为…」 |
| `default` | 只有本地抽取 | 写结构化标题，`title_source=auto_local`，不飘 toast |
| `default` | 内容太短 / 全闲聊 | **不改名**，只存候选（避免 `5 人连麦` 变成正式名字） |
| `auto` | 新总结出标题且与当前不同 | 更新主标题（系统起的，可以更新），列表静默刷新，不重复 toast |
| `auto_local` | 这次有 LLM 标题 | 升级为 `auto`，并提示一次 |
| `user` | 任意 | **永不覆盖**，只更新 `title_alts_json` |
| `legacy` / `demo` | 任意 | 不覆盖，只存候选 |

两条补充规则：

- **用户改名即锁定**：`/api/sessions/rename` 一律写 `title_source=user`。
- **采纳候选也算用户决定**：点「采用」走 `/api/sessions/title/adopt`，同样写 `user`，此后不再被自动刷掉。

并发保护：`_auto_finalize` 的线程里，写回前重读一次 `title_source`；如果已被用户改成 `user`，直接丢弃（返回 `title_applied=false`），不覆盖。

### 3.4 接口变化

| 接口 | 变化 |
| --- | --- |
| `POST /api/summarize` | 返回体增 `title` / `title_alts` / `title_applied` / `title_source`；标题写回由服务端按 3.3 决定（前端不猜） |
| `GET /api/sessions/suggest_title` | 语义改为**读缓存**：最近一次 summary 的 `title+alts` → 其次清洗后的原话摘录 → 最后结构化。默认 **0 次模型调用** |
| `GET /api/sessions/suggest_title?fresh=1` | 只有「换一个」按钮用；显式计费提示「将再调用一次模型」；仅在配置了 LLM 时有效 |
| `POST /api/sessions/rename` | 不变，但写 `title_source=user` |
| `POST /api/sessions/title/adopt` | 新增：`{session_id,title}` → 写 `user`，返回新场次信息 |

### 3.5 UI 调整

**(1) 总结面板顶部「标题条」**（在 overview 之上，一行，不抢要点空间）：

```
🏷 大棚菜销路：连麦里问最多的三个坑            [采用] [换一个]
   五个人聊大棚：谁在赚谁在亏 · 从种到卖，卡在哪一步
```

- 已采用时：`[采用]` 变成 `✓ 已采用`，`✎` 仍在顶部会话栏
- 窄面板下第二行自动折行，最多两行，超出省略
- `title_applied=false` 时整条变灰，并注明原因（`你已命名，未覆盖`）

**(2) 改名弹层重排成三组，每个候选带来源标签**：

| 组 | 内容 | 样式 |
| --- | --- | --- |
| AI 起的名 | 来自本次总结，**不重新请求** | 主按钮样式 |
| 原话摘录 | `_clean_quote` 产物，前缀「原话：」 | 次按钮 + 灰色标签 |
| 结构信息 | `5 人连麦` | 弱化，默认收起 |

- 候选**一律去掉 ` · 03:41` 尾巴**（`stamp()` 删掉）
- 弹层打开时 0 网络请求；只有点「换一个」才发 `fresh=1`
- 输入框默认全选当前名，直接输入即覆盖

**(3) 顶部 / 列表 / 图书馆**：改名后即时刷新（已有逻辑）；列表行尾加小徽标 `AI` / `手动`，点徽标可直接"恢复自动标题"。

**(4) 实时监听中不改名**：直播进行时标题会跳，结束时统一处理（`_auto_finalize` 已经是这个时机，保持）。

### 3.6 降级链（无 LLM / 调用失败 / 内容太短）

1. **LLM 标题**（总结调用内，0 额外请求）
2. **结构化**：`{人数} 人连麦 · {topic_top1}`——`topic` 来自 `TOPIC_RULES` 统计，比裸 `5 人连麦` 多一档信息
3. **摘录**：清洗后的原句，前缀「原话：」，明确标注不是标题
4. **保留默认名**（不动）

任何一级输出经 `_clean_title()` 校验：去引号/书名号、折叠空白、去句末标点、截 24 字；空、纯标点、与当前同名 → 跳到下一级。

### 3.7 边界条件清单

| 场景 | 期望行为 |
| --- | --- |
| 用户先改名，后生成总结 | 不覆盖，只更新候选；`title_applied=false`，UI 注明原因 |
| 总结生成中用户改名 | 写回前重读 `title_source`，已是 `user` 则丢弃 |
| 同一场多次生成（换模式/筛选/维度） | 只更新候选并去重；主标题仅在 `auto` 态允许更新 |
| 内容太短（< 15 条或 < 400 字） | 不调 LLM（沿用 `_worth_llm`）；不自动改默认名 |
| 全是闲聊 / 广告 / 控场 | LLM 返回 `title:null` → 结构化 → 仍不合格则保留默认名 |
| 未配置 LLM | 抽取式总结 + 结构化标题，`auto_local`，设置页与 ebar 明示「本地生成，0 token」 |
| 同一天多场同名 | **不加时间后缀**（时间在副行）；导出文件名用 `标题-YYYYMMDD-HHMM.ext` 去重 |
| 标题超长 / 含换行 / emoji / 引号 | 清洗后截断 24 字；非法则降级 |
| 中英混排、纯英文 | 允许；长度按字符计，不强制汉字 |
| 场次删除 / 还原 / 清空回收站 | 标题随行，无额外逻辑 |
| 演示数据（`source_mode=demo`） | 视为 `legacy`，不自动改名 |
| 重聚类 / 改说话人之后 | **不自动改名**（可能已采纳），改由用户点「换一个」显式触发 |
| 总结成功但标题非法 | 只缺标题，不阻塞总结，不抛错 |
| 改名失败 / 网络断开 | 只回滚标题，不动逐字稿与总结 |
| token 计量 | 标题增量并入同一次 `usage`，ebar 显示 tokens 已含标题，不额外记账 |

### 3.8 成本账

| | 现状 | 改后 |
| --- | --- | --- |
| 结束一场 | 2 次调用（40 句抽样 + 最多 800 句总结） | 1 次调用，输出 +~50 token |
| 打开改名 | 1 次调用 | 0 次 |
| 改名开 3 次 | 共 5 次 | 1 次 |

粗算：输入侧省掉"40 句抽样"和"改名重传"，整场从 3–5 次降到 1 次，**约省 60%–85% 的标题相关 token**；而且省下来的不是钱的问题——是标题第一次能看到全局。

## 5. 验收标准

1. 结束一场并生成总结：服务端日志里**只有 1 次** LLM 请求（`usage` 也只记 1 次）。
2. 打开改名弹层：Network 面板 **0 个请求**，候选与总结一致且不带时间尾巴。
3. 先手动改名 → 再生成总结 → 标题不变，候选更新，`title_applied=false` 且原因可见。
4. 不配置 LLM → 有结构化标题（含 topic），界面提示"本地生成"，不报错。
5. 内容 < 15 条的场次 → 不调模型，保留默认名，弹层里只给摘录。
6. 标题断言：长度 ≤ 24 字符、无换行、无句末标点、不等于默认名前缀、重复候选被去重。
7. 同一天 3 场同名场景：列表可区分（副行时间），导出文件名不冲突。

---

## 6. 取舍与不做

- 不做「标题历史版本」：v1 只保留最近一次候选，够用。
- 不做候选相似度去重（embedding）：长度短、收益低，用字符串去重即可。
- 不做 A/B 或点击率回收：样本太小。
- 本期只加 `title`，**不加** `tags` / `关键词`：同一 JSON 里加字段很容易变成"顺手需求膨胀"，等标题稳定后再议。
- 标题刻意偏"主播视角/回看者视角"：这个产品的读者是事后复盘的人，不是直播间里的观众。

与设计稿的差异（都是有意的）：

1. **标题条会自己消失**：名字已经是当前名、又没有备选，或者结论是「内容太少 / 本地只算出人数」时，不占位置——噪音比信息更贵。
2. **`fresh=1` 的入口放在标题条「换一个」**，不放在改名弹层：弹层保持 0 请求。
3. **旧库的「名字 · 03:41」判为 `auto` 而不是 `legacy`**：这类是旧规则自动起的，应该允许新总结把它换掉；判断依据是「结尾是 ` · HH:MM` 且从未被新 UI 改过（`title_updated_at` 为空）」。

尚未做：`library.html` 的「AI / 手动」徽标；阅读页 `reader.html` 仍是原生 `prompt()`（但它已经走缓存，0 token）。
