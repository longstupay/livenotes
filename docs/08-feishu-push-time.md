# 飞书推送：时间该显示什么、什么时候推

> 触发场景：飞书里收到的卡片第一行是 `💡 9:09 · 阿哲`。9:09 是**录音里的第 9 分 09 秒**，
> 不是任何真实时间。用户问了两件事：
> 1）能不能给北京时间、UTC 时间（两个都要）；
> 2）正在监听时能不能推，还是必须点「结束」才推？

## 结论先说

- **时间**：推送里同时给「北京」和「UTC」，日期一起带上；录音内偏移保留，用来跳转回听。
  场次开始时把 `started_utc` + `tz_offset_min` 落库，之后机器搬到哪个时区都不影响换算。
- **时机**：**监听中就会推**，不需要点结束。但旧实现有三层延迟叠加，看起来像"只有结束时才推"：
  45 秒峰值等待、30 分钟冷却、以及"结束时不 flush、最后一条直接丢"。
  现在：这段话说完了（静音 45 秒）就推；结束时会补一条「本场高光回顾」，只列没推到的。

## 一、为什么是三套时间，而不是一套

| 时间轴 | 例子 | 谁在用 | 能不能去掉 |
|---|---|---|---|
| 录音内偏移 | 9:09 | 回听链接 ?t=549、逐字稿时间轴 | 不能，跳转只认它 |
| 北京时间 | 01-01 20:04:38 | 人对表、对聊天记录、跟同事说"就刚才那段" | 不能，用户在这个时区 |
| UTC | 12:04:38 | 跨系统对日志、跨时区协作、以后接数据平台 | 不能，唯一无歧义 |

只给偏移：用户不知道"这是几点说的"，尤其隔了几个小时再翻聊天记录。
只给北京时间：机器/服务换到别的时区（出差、云主机、同事复现）就会算出两个"北京时间"。

### 换算规则（app/timefmt.py）

1. 新场次开始那一刻，记 `started_utc`（带 +00:00）和 `tz_offset_min`（东八区 = 480）。
2. 任何时刻 t：UTC = started_utc + t，北京 = UTC + 8h（北京无夏令时，固定 +08:00）。
3. 没存时区的老数据：用 started_at + 本机时区兜底。**不猜一个 UTC 写回库**——
   写错的历史数据比"可能差一小时"更难查。
4. 日期永远带上（11-05）。跨零点时北京是 11-06 00:05、UTC 还是 11-05 16:05，
   只写时分会被读成同一天。两边日期不同时，两边的日期都写。

### 边界

- **跨零点 / 跨年**：日期都带；不是今年的再补年份。
- **长直播**：录音内偏移超过 1 小时改成 1:02:05，否则 2 小时 5 分会写成 125:03，像另一场的编号。
- **机器时区不是东八区**：以落库的 tz_offset_min 为准，与本机当前时区无关。
- **夏令时**：北京没有；如果录制机器在有夏令时的时区，落库的是录制当时的固定偏移，
  一场直播中途切换也不会跳变。
- **时区库缺失（Windows 没 tzdata）**：用固定偏移实现，不 import zoneinfo。

## 二、什么时候推：实时 vs 结束

### 旧实现的四个问题

1. **45 秒峰值等待**：OnlineScorer 会压住一段里分数最高的那句，等"下一句"到来才发。
   直播一冷场、或者用户说完就关标签页，这条永远发不出去。
2. **flush() 没人调用**：OnlineScorer.flush() 写好了，但全仓库没有调用点——
   点「结束」时最后一条不是"晚点推"，是**直接丢**。
3. **30 分钟冷却 + 每天 3 条**：两小时的直播最多 3 条，第二段之后还要再等半小时，
   实战里经常一场只响一次，用户会以为"根本没在推"。
4. **额度按"尝试"算**：发送前就自增，飞书一次网络抖动就白瞎当天一条额度；
   计数器在进程内存里，重启就清零。

### 现在的链路

    每 4 秒一句 -> 打分 -> 命中(>=2.5 且 >=8 字)
      ├─ 分数 >= 3.2（极高）       -> 立刻推
      ├─ 普通命中                  -> 压 45 秒，取这段峰值
      │    ├─ 下一句到来且超过 45s -> 推
      │    ├─ 静音/暂停/关页 45s   -> 推（worker 每 0.25s 轮询）
      │    └─ 点「结束」           -> 收尾 flush（不再受冷却拦截）
      └─ 同一条（session_id + peak_t）只推一次：push_log 唯一索引

发送前依次过：单场实时上限（默认 3 条）→ 当日预算（默认 5 条，只算发成功的）→ 飞书。
任何一步失败只写 push_log，**绝不影响录音与字幕**。

### 结束时的「本场高光回顾」

- 只列**实时没推到的**（最多 3 条），已推过的不会再列一遍——那些消息还在聊天记录里。
- 全部推过 → 静默，不为了"有始有终"再发一条。
- 取消的场次（/api/live/cancel）不发任何推送。
- 回顾不占实时推送的每日额度：它是收据，不是打断。

## 三、消息长什么样

实时：

    💡 阿哲 · 01-01 20:04:38 北京 / 12:04:38 UTC
    录音 9:09 · 抢麦；提到 2 处数字/金额；结论句
    「我建议先做一次模拟面试录音回听，看看真实情况。」
    回听：http://192.168.1.10:8765/reader?session=LIVE_20260101_120000&t=549

收工回顾：

    🎬 本场高光补推 2 段 ·《示例直播复盘》
    01-01 20:00:00 北京 / 12:00:00 UTC 开始 · 共 12 条入榜，实时推过 1 条
    1. 01-01 20:02:10 北京 / 12:02:10 UTC · 嘉宾 · 录音 2:10
    「……」
    回听：http://…/reader?session=…&t=130

网页这边（阅读页时间轴、高光榜时间码）也补了同一套墙钟：鼠标悬停时间码会显示
「北京 01-01 20:04:38 / UTC 12:04:38」。数据用 /api/reader 里新带的 started_utc
换算，老场次没有该字段时按本机时区解释。

## 四、卡片：时间做成字段，回听做成按钮

实时推送和收工回顾都发 interactive 卡片：

    ┌ 💡 阿哲 · 直播高光 ─────────────────┐
    │ 北京时间             UTC              │
    │ 01-01 20:04:38       01-01 12:04:38   │
    │ 录音 9:09 · 抢麦；提到 2 处数字…        │
    │ 「我建议先做一次模拟面试录音回听……」        │
    │  [ 回听这一段 ] [ 👍 有用 ] [ 👎 没用 ] │
    └────────────────────────────────────────┘

为什么值得：手机上不用长按复制链接，点按钮直接进阅读页那一刻；时间也从一行
文字变成两个字段，扫一眼就能对上表。

👍/👎 是 URL 按钮，点开落在本机 /card/feedback：记下、显示"下一场这类会少推"，
关掉即可。为什么不做真回调：飞书卡片回调要求公网可达的地址，和"纯内网"冲突；
URL 按钮在飞书里点开就是访问本机服务，不需要任何外网配置。

**但卡片是"锦上添花"，不能成为单点故障。** 飞书卡片 schema 随客户端/租户权限
变化，字段写错会直接发送失败。所以：

- 卡片发送失败 → 自动回退纯文本重发，push_log 记 sent + reason=card_fallback；
- 实际发出的卡片 JSON 存在 push_log.card_json，改版后能复盘"当时到底发了什么"；
- LIVENOTES_PUSH_CARD=0 可一键退回纯文本。

## 五、反馈闭环：你标过"没用"的那类，少打断你

高光打分回答的是"这段内容像不像值得听"，不是"这个人觉得值不值得听"。
没有闭环，用户每标一次 👎，下一次同样的句式还会照样响——久了他会关通知，
而不是继续标。

规则（app/feedback.py，刻意做得可解释、可回退）：

| 项 | 规则 |
|---|---|
| 信号 | 高光榜上的 👍/👎（highlights.feedback） |
| 粒度 | 特征标签：提到数字/金额、结论句、接住提问、长段陈述、语速陡增、抢麦、短句连发 |
| 门槛 | 每个标签至少 3 个样本才生效；好评率 ≤1/3 抬 0.4 分，≥2/3 降 0.2 分；单条事件合计偏置 ±0.6 封顶 |
| 生效时机 | **下一场开始**时加载；同一场中途不改口（否则用户会觉得"时灵时不灵"） |
| 表现 | 不是拉黑，是"这类要在本场更突出才值得打断"——热点仍然漏不掉 |
| 可见 | 高光榜底部："推送偏好（按你的 👍/👎 学，下一场生效）：提到数字/金额 更少推（1👍/4👎）" |
| 来源 | 网页打标 + 卡片上的 👍/👎（同一段两边都标时以卡片为准） |

## 五之二、为什么这条没推：台账页

/pushes 一场一页，回答两个问题：**推了什么**、**没推是为什么**。

- 每行：时间、结果（已发 / 未推 / 失败）、正文摘要、原因；
- 预算条：今日 x/5、本场实时 x/3、冷却分钟数、已学到的偏好；
- 原因码：cooldown（距上条太近）、session_cap（本场推满）、daily_cap（今日额度）、
  learned_bias（这类你标过没用）、no_open_id / no_bot（没配接收人）、
  send_fail、card_fallback（卡片被拒已回退文本）。

"没推"的记录不再只是 SQL：push_log 里 status=skipped 的每一行都带原因，
页面直接翻译成人话。入口在阅读页/高光榜顶部的「📣 推送」。

## 六、配置（环境变量）

| 变量 | 默认 | 说明 |
|---|---|---|
| LIVENOTES_PUSH | 1 | 总开关 |
| LIVENOTES_PUSH_COOLDOWN | 600 | 两条实时推送的最小间隔（录音内秒） |
| LIVENOTES_PUSH_SESSION_CAP | 3 | 单场实时推送上限 |
| LIVENOTES_PUSH_CAP | 5 | 每天成功推送上限（不含回顾） |
| LIVENOTES_PUSH_DIGEST | 1 | 结束时发「补推回顾」；关掉则只补最后一条 |
| LIVENOTES_PUSH_CARD | 1 | 发 interactive 卡片；关掉退回纯文本 |

调参思路：先保时效（45 秒内），再保不烦（单场 3 条）。这两条冲突时，
让回顾去兜底，而不是提高实时推送频率。

## 七、边界与对策

| 场景 | 行为 |
|---|---|
| 用户关掉标签页、不点结束 | 音频断流 45 秒后把 pending 推出去；场次保持"监听中"，可手动结束 |
| 卡片被飞书拒绝 | 回退纯文本重发，记 sent + card_fallback；不会丢消息 |
| 反馈样本不足 3 条 | 该标签不生效，门槛保持原样（宁可不动，也不要一票否决） |
| 用户按暂停 | 暂停期间不再产生新事件；已压着的那条留到恢复或结束时补发 |
| 飞书没配凭证 / 没记 open_id | push_log 记 failed: no_bot / no_open_id，不重试、不阻塞 |
| 网络失败 | 记 failed: send_fail；该条不会重发，但会出现在回顾的"未推"里 |
| 进程重启 | 额度从 push_log 重新算；同一 (session_id, peak_t) 不会重复发 |
| 同一条高光被并发触发 | 唯一索引抢占，只有一个线程真正发送 |
| 一场 4 小时、高光很多 | 单场 3 条 + 每日 5 条封顶，其余进回顾 |
| 取消的场次 | 不推任何消息（含回顾） |
| 时区/日期 | 北京与 UTC 都带日期，跨零点不会歧义 |

## 八、怎么验收（不用等下一场直播）

    python tools/push_preview.py                          # 样例：纯文本 + 卡片 JSON + 回顾
    python tools/push_preview.py LIVE_20260101_120000     # 指定场次：文案 + 推送记录 + 已学偏好

推送台账（为什么没收到，一查便知）：

    SELECT session_id,item,status,reason,created_at FROM push_log ORDER BY id DESC LIMIT 20;

status：sent 已发 / failed 失败 / skipped 没推。原因在 reason：
cooldown / session_cap / daily_cap / learned_bias / no_open_id / no_bot / send_fail / card_fallback。
页面（/pushes）会把这些码翻成人话。

## 九、还没做的

- 卡片 schema 已在真实租户实发验证（2026-11-05），文本回退仍在；回顾卡的多按钮
  排版还没单独验过。
- 👍/👎 的落点是 URL 页面（/card/feedback），因此手机必须能访问到本机服务
  （同一局域网）。异地点击会打不开——这在"纯内网"前提下是有意取舍。
- 网页时间轴的墙钟时间靠 title（悬停）展示，触屏设备看不到。手机上要不要
  直接显示"17:04"这一列，等排版定了再说。
- 推送台账 /pushes 只做"看"，还不能一键重发失败的那条。
